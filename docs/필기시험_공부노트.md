# 내 게임으로 공부하는 C# 필기시험 노트

기준: 현재 `src/ActionGame` 코드. 실제 출제 범위는 수업 안내를 우선한다.
이 노트는 코드를 외우기보다 “입력 → 값 변화 → 화면 결과”를 설명하도록 구성했다.
교수님 glc2d, 게임 코드, 개발용 테스트 코드를 구분해서 읽는다. 테스트의 Reflection은 게임 구현의 필수 공부 순서에 포함하지 않는다.

바로 GameMain.cs부터 공부하려면 **18장 「GameMain.cs 처음부터 끝까지 — 코드 순서대로 읽기」**를 먼저 읽는다. 원본 코드에 배치된 순서대로 42개 소단원으로 설명했다.

**파일별 코드 순서 해설:** 18장 GameMain.cs · 19장 Player.cs · 20장 Enemy.cs · 21장 GameHud.cs · 22장 GameAssets.cs · 23장 GameRules.cs · 24장 GameEffect.cs · 25장 ScorePopup.cs · 26장 Program.cs · 27장 GameGlobal.cs. 각 장은 실제 파일의 위에서 아래 순서로 읽는다.

## 2. 클래스와 객체

`Player`는 플레이어 정보의 설계도이고 `new Player()`는 실제 정보를 담는 객체를 만든다.
`player.Hp`는 그 객체의 체력 필드이다. Enemy 목록에는 서로 다른 Enemy 객체가 들어 있다.

```csharp
Enemy a = new Enemy(150, 180);
Enemy b = new Enemy(700, 180);
a.Hp -= 1;
```

두 적은 각각 만들어졌으므로 a의 체력만 2→1로 줄고 b는 2이다.
반대로 `Enemy b = a;`라면 같은 객체를 가리키므로 b에서 읽어도 체력이 1이다.
생성자 Enemy(float x, float y)는 전달받은 위치를 X, Y 필드에 저장한다.

## 4. 실행 순서와 상속

```text
Program.Main
  → ApplicationConfiguration.Initialize
  → new GameMain
  → game.Run (부모 G2AppBase)
      → Initialize 한 번
      → 입력 갱신 → Update → Render 반복
  → 창 닫힘 → using이 Dispose 호출
```

GameMain은 G2AppBase를 상속한다. 창·입력·그리기 장치 같은 공통 처리는 부모가 제공하고, 자식은 게임별 초기화·규칙·화면을 구현한다. 이것이 이 프로젝트의 상속 예다.

Player와 Enemy를 GameMain이 필드·목록으로 가지고 있는 관계는 상속이 아니라 객체를 포함하는 관계다.

## 6. dt와 이동 계산

`dt`는 이번 프레임에서 반영하는 시간(초)이다. 이동은 `dx * player.Speed * dt`이다.

속도 240, 오른쪽 방향 dx=1, dt=0.016이면 X는 3.84 증가한다. 1초에 60번 갱신되는 경우 dt가 약 1/60이면 프레임마다 약 4씩 움직여 1초에 약 240을 이동한다.

오른쪽 위로 이동하면 dx=1, dy=-1, 길이는 √2이다. 각각 √2로 나누면 약 (0.707, -0.707)이 된다. 그대로 (1, -1)을 사용하면 대각선 속도가 √2배 빨라진다.

`if (length > 0)`은 입력이 없을 때 0으로 나누는 것을 막는다.
`Math.Clamp`는 플레이어의 중심을 벽에서 반지름만큼 안쪽에 제한해 몸이 밖으로 나가지 않게 한다.

실습: 시작 X=310, D 키, Speed=240, dt=0.05이면 다음 X는 322이다.
주의: 코드가 dt를 최대 0.05로 제한하므로 긴 프레임 정지 후 현실 시간 전체를 한꺼번에 반영하지 않는다.

## 7. 킥의 판정과 넉백

오른쪽 방향 (1, 0), 플레이어 (310, 320)이면 킥 중심은 (352, 320)이다.
킥 반지름 38, 적 반지름 18이므로 중심 거리가 56보다 작으면 맞는다. 코드가 `<`이므로 정확히 56이면 맞지 않는다.

Kick은 적 Hp를 1 줄이고 LaunchEnemy를 호출한다. LaunchEnemy는 VelocityX/Y에 방향×600을 넣고 FlyTime=0.65를 저장한다. 다음 MoveEnemies가 `좌표 += 속도 × dt`로 움직인다.

이동 뒤 속도에 `Exp(-2 * dt)`를 곱한다. 이 비율은 양수이고 1보다 작아서 점점 느려진다. 지수 함수를 사용한 감속은 여러 작은 dt로 나누었을 때도 비슷한 결과가 난다.

KickCooldown이 0보다 크면 return하여 연속 공격을 막는다. Update는 매 프레임 쿨다운에서 dt를 빼되 0 아래로 내려가지 않도록 한다.

## 8. 적끼리 충돌과 HashSet

바깥 foreach는 날아가는 적, 안쪽 foreach는 맞을 수 있는 다른 적이다. 자기 자신·죽은 적·이미 맞힌 적은 건너뛴다.
날아가는 적의 HitEnemies에 상대 객체를 넣어 겹쳐 있는 여러 프레임 동안 중복 피해를 주지 않는다.
새로 날아갈 때 HitEnemies.Clear를 호출하여 다음 공격에서는 다시 맞힐 수 있게 한다.

HashSet은 중복 없이 저장하는 자료구조다. List는 순서대로 여러 항목을 보관하기 좋고, Dictionary는 이름을 키로 값을 찾기 좋다.

| 실제 사용 | 자료구조 | 이유 |
| --- | --- | --- |
| enemies | List<Enemy> | 적 수가 변하고 전체 순회·제거 필요 |
| HitEnemies / shockedEnemies | HashSet<Enemy> | 이미 피해를 받은 상대 확인 |
| images / sounds | Dictionary<string, ...> | 파일 역할 이름으로 리소스 찾기 |

## 9. 전기 바닥 추적 문제

`phase = roundTime % 6`이다. 0~2.5 미만은 대기, 2.5~4 미만은 경고, 4~6 미만은 작동이다.

| roundTime | phase | 상태 |
| --- | --- | --- |
| 2.4 | 2.4 | 대기 |
| 2.5 | 2.5 | 경고 시작 |
| 4.0 | 4.0 | 작동 시작 |
| 6.0 | 0 | 다시 대기 |
| 10.1 | 4.1 | 작동 |

전기는 2라운드부터 피해를 준다. 3라운드는 가로 영역도 추가한다.
플레이어는 InvincibleTime으로 연속 피해를 제한한다. 적은 shockedEnemies로 한 작동 구간당 한 번만 피해를 받는다. 두 방식은 다르다: 플레이어는 전기 안에서 1초 뒤 또 맞을 수 있다.

`wasHazardActive`는 켜진 첫 프레임에만 시작 스파크와 효과음을 내기 위해 이전 상태를 기억한다.

## 10. 목록에서 뒤로 지우는 이유

적 목록이 [A(죽음), B(죽음), C(생존)]이라고 하자.
앞에서 A를 지우면 B가 인덱스 0으로 옮겨진다. 여기서 i를 1로 올리면 B를 건너뛸 수 있다.
뒤에서 시작하면 C 검사 → B 제거 → A 제거이므로 아직 검사하지 않은 앞쪽 인덱스는 유지된다.

현재 코드의 for문: `int i = enemies.Count - 1; i >= 0; i--`.
효과·점수 팝업 삭제에도 같은 원리를 사용한다.

## 11. 점수 계산 예제

적 처치 100점, 적끼리 연쇄 충돌 50점이다. AddScore는 실제 점수를 더한 뒤 표시용 ScorePopup을 추가한다. 글자가 사라져도 실제 점수는 줄어들지 않는다.

12.9초, 남은 체력 3으로 라운드 완료:

```text
정수 시간 = 12
시간 보너스 = 600 - 12 × 10 = 480
체력 보너스 = 3 × 50 = 150
라운드 보너스 = 300 + 480 + 150 = 930
정비 후 체력 = min(5, 3 + 1) = 4
실제 회복량 = 4 - 3 = 1
```

75초, 체력 5이면 시간 보너스 0, 라운드 보너스 550, 정비 후 체력 5, 실제 회복량 0이다.
체력을 먼저 회복시키고 보너스를 계산하면 첫 예에서 50점이 더해지므로 순서가 중요하다.

## 12. 애니메이션과 UI

GameEffect는 Age(지난 시간) / Duration(전체 시간) × 4로 프레임을 정한다.
Duration=0.4, Age=0.25이면 2.5를 정수로 바꿔 2번 프레임이다.
2×2 시트의 열은 `frame % 2`, 행은 `frame / 2`이다. 여기서 두 피연산자가 정수이므로 `/`의 소수 부분은 버려진다.

프레임 3, 한 칸 128이면 원본 시작점은 (128, 128)이다.
전기 타일은 별도의 627픽셀 칸을 사용한다. 모든 시트가 같은 크기는 아니다.

ScorePopup은 Y에서 30×dt를 빼고 Life에서 dt를 뺀다. 화면 Y는 아래로 증가하므로 글자가 위로 올라간다. Life≤0이면 목록에서 제거한다.
HUD 진행률은 `1 - (float)remaining / total`이다. 6대 중 3대가 남으면 0.5다. float 변환이 없으면 정수 나눗셈이 되어 잘못된 막대가 된다.

## 13. 그리기와 자원 관리

GameAssets는 이미지를 Dictionary에 한 번 로딩해서 재사용한다. 매 프레임 파일을 읽으면 불필요한 작업이 많아진다.
스프라이트 회전은 현재 Transform 저장 → 회전·이동 적용 → 그리기 → finally에서 원래 값 복구 순서다. 복구하지 않으면 이후 HUD도 회전할 수 있다.

Dispose는 이미지·사운드·폰트·붓 같은 자원을 해제한다. GameMain은 자신의 자원을 먼저 정리하고 `base.Dispose()`로 부모의 장치를 나중에 정리한다.
C#의 가비지 컬렉터가 관리 객체 메모리를 정리하더라도 그래픽·오디오 장치의 자원 해제를 적절한 시점에 보장하기 위해 Dispose를 사용한다.

## 14. 예상 서술형 문제와 핵심 답

1. **Update와 Render를 분리하는 이유?** Update는 게임 상태 변경, Render는 현재 상태 출력이다. 그리기 횟수 때문에 피해·점수가 달라지지 않게 한다.
2. **이동에 dt를 곱하는 이유?** 프레임마다 일정 거리 대신 실제 경과 시간에 비례해 이동하게 하려는 것이다.
3. **대각선 정규화 이유?** (1,1)의 길이가 √2이므로 그대로 쓰면 대각선이 더 빠르기 때문이다.
4. **IsKeyDown과 IsKeyPress 차이?** 처음 누른 순간과 계속 누르는 상태다. 킥은 전자만, 이동은 둘 다 확인한다.
5. **HashSet이 필요한 이유?** 이미 맞은 적을 기록해 같은 공격의 중복 피해를 막는다.
6. **새 라운드에 Player를 다시 만들지 않는 이유?** 이전 체력을 유지해야 하기 때문이다.
7. **왜 죽은 적을 뒤에서 제거하는가?** 삭제로 앞으로 이동한 원소를 건너뛰지 않기 위해서다.
8. **왜 패배를 먼저 검사하는가?** 동시에 마지막 적과 플레이어가 죽으면 패배로 처리하는 규칙 때문이다.
9. **보너스를 반복 지급하지 않는 이유?** 완료 시 상태를 바꾸고 Playing이 아닌 경우 종료 판정을 건너뛴다.
10. **readonly List에 Add가 가능한가?** readonly는 목록 참조 재대입을 막고 내부 원소 변경까지 막지는 않는다.
11. **Dictionary와 List 차이는?** Dictionary는 키로 조회하고, List는 순서·인덱스로 항목을 다룬다.
12. **const와 일반 필드 차이는?** const는 정해진 값을 변경할 수 없고 일반 필드는 플레이 중 상태를 저장·변경한다.
13. **전기 경고와 실제 피해를 분리한 이유?** 위험을 미리 보여 주되 작동 시간에만 피해를 주기 위해서다.
14. **발차기 방향을 저장하는 이유?** 움직임이 멈춰도 마지막 방향으로 공격할 수 있어야 한다.
15. **그리기 변환을 복구하는 이유?** 한 캐릭터의 회전·이동이 다음 오브젝트에 영향을 주지 않게 한다.
16. **Math.Max(0, ...) 이유?** 시간·보너스 등이 음수로 내려가지 않도록 제한한다.
17. **점수 팝업과 실제 점수를 분리한 이유?** 화면 효과의 수명과 기록 점수의 수명이 다르기 때문이다.

## 18. GameMain.cs 처음부터 끝까지 — 코드 순서대로 읽기

이 장은 `src/ActionGame/GameMain.cs`의 실제 배치 순서를 따른다. 왼쪽에 코드를 열고 오른쪽에 이 문서를 열어서 같은 이름을 찾으며 읽자. 줄 번호는 코드가 수정되면 달라지므로 함수 이름을 기준으로 찾는다.

**먼저 알아둘 점:** 파일에 적힌 순서와 실행되는 순서는 다르다. 함수는 아래에 적혀 있어도 호출하면 실행된다. 필드 초기화 후 부모의 Run이 Initialize를 한 번, Update와 Render를 반복해서 호출한다. AddEffect가 파일 위쪽에 있다고 해서 프로그램 시작 시 먼저 실행되는 것은 아니다.

### 18-01. using 세 줄: 필요한 도구의 이름을 가져오기

```csharp
using System.Numerics;
using Vortice.Direct2D1;
using Vortice.Mathematics;
```

`using`은 다른 곳에 정의된 형식의 긴 이름을 짧게 쓸 수 있게 한다. 이 세 줄 자체가 게임을 실행하지는 않는다.

- System.Numerics: `Vector2`처럼 좌표 두 개를 묶는 형식에 사용한다.
- Vortice.Direct2D1: 붓, 원 그리기 등 Direct2D 그래픽 형식에 사용한다.
- Vortice.Mathematics: `Rect`, `Color4` 같은 사각형·색 형식에 사용한다.

List, Math, Form 등의 using이 여기 보이지 않는 이유는 프로젝트의 ImplicitUsings/Windows Forms 설정이 일부 using을 자동으로 추가하기 때문이다.

### 18-02. namespace와 클래스: 이 파일의 소속과 역할

```csharp
namespace ActionGame
{
    internal class GameMain : G2AppBase
```

`namespace ActionGame`은 이 게임의 형식들을 묶는 이름 공간이다. 다른 라이브러리에 같은 이름의 클래스가 있어도 소속을 구분할 수 있다.

`class GameMain`은 게임 진행을 담당할 클래스 선언이다. `internal`은 같은 어셈블리 안에서 접근할 수 있다는 뜻이다. `: G2AppBase`는 교수님 프레임워크 클래스를 상속한다는 뜻이다. 부모가 창, 입력, 그래픽 장치를 준비하고 GameMain은 구체적인 게임 동작을 구현한다.

중괄호 `{ }`는 소속 범위를 나타낸다. 클래스 중괄호 안에 있는 필드·함수는 GameMain의 구성원이다.

### 18-03. player와 enemies: 게임에 등장하는 객체

```csharp
private Player player = new Player();
private List<Enemy> enemies = new List<Enemy>();
```

첫 줄을 나누어 읽으면 다음과 같다.

| 부분 | 뜻 |
| --- | --- |
| private | GameMain 내부에서 관리한다 |
| Player | 저장할 값의 형식이다 |
| player | 필드 이름이다 |
| = | 오른쪽 값을 왼쪽에 대입한다 |
| new Player() | 새 플레이어 객체를 만든다 |

두 번째 줄의 `List<Enemy>`는 Enemy 객체를 여러 개 보관하는 목록이다. `<Enemy>`는 이 목록에 담는 항목의 형식을 뜻한다. `new List<Enemy>()`는 빈 목록을 만든다. 이 시점에는 적 객체가 아직 들어 있지 않다. 실제 적 생성은 StartRound에서 한다.

`player`는 플레이어 하나를 가리키고, `enemies`는 적들의 목록을 가리킨다는 차이를 기억하자.

### 18-04. ScreenSize와 GameName: 부모가 읽을 설정

```csharp
public override System.Drawing.Size ScreenSize => GameGlobal.ScreenSize;
public override string GameName => GameGlobal.GameName;
```

이것은 필드가 아니라 **읽을 때 값을 돌려주는 속성**이다. `=>`는 짧게 쓴 표현이다.

```csharp
// 뜻을 풀어 쓴 예시. 원본을 바꿀 필요는 없다.

```

부모 G2AppBase가 GameName을 읽으면 GameGlobal에 적힌 게임 이름을 받는다. `override`는 부모에 정의된 속성의 동작을 자식이 바꿔 제공한다는 뜻이다. 화면 크기는 현재 900×620이다.

### 18-05. brush, arena, score: 붓·경기장·점수

```csharp
private ID2D1SolidColorBrush? brush;
private RectangleF arena = new RectangleF(30, 90, 840, 480);
private int score = 0;
```

brush는 도형을 칠할 붓이다. `?`가 있으므로 아직 준비되지 않은 null 상태도 허용한다. 실제 붓 생성은 그래픽 장치가 준비된 Initialize에서 한다.

### 18-06. GameState, state, gameEnded: 지금 어느 화면인가

```csharp
private enum GameState { Lobby, Playing, RoundClear, Result, Paused }
private GameState state = GameState.Lobby;
private bool gameEnded => state != GameState.Playing;
```

enum은 사용할 수 있는 상태에 이름을 붙인다. state에는 그중 하나가 들어간다. 첫 상태는 Lobby다.

`!=`는 “같지 않다”이다. gameEnded는 읽을 때마다 state가 Playing이 아닌지 계산한다. 이름만 보면 종료 여부 같지만 **현재 코드에서는 로비·정비·일시정지도 true**다. 주로 걷기 애니메이션을 전투 외 상태에서 멈추는 데 사용한다.

준비 시간 중에는 state가 Playing이므로 gameEnded가 false다. 다만 Update가 준비 시간에서 return하여 전투는 움직이지 않는다. 변수 이름만 보고 판단하지 말고 실제 조건식을 읽자.

### 18-08. 전기 관련 필드·속성·함수

```csharp
private readonly HashSet<Enemy> shockedEnemies = new();
private float HazardPhase => roundTime % GameRules.HazardCycle;
private bool HazardActive => round >= 2 && HazardPhase >= GameRules.HazardStart;
```

shockedEnemies는 이번 전기 작동 중 이미 맞은 적을 저장하는 집합이다. `new()`는 `new HashSet<Enemy>()`의 짧은 표현이다. readonly는 다른 집합으로 다시 대입하지 못하게 하지만 Add, Clear로 내용은 바꿀 수 있다.

`%`는 나머지 연산이다. 6초 주기라면 roundTime=10.1일 때 HazardPhase는 약 4.1이다. float 연산이므로 소수 표현에는 작은 오차가 있을 수 있다.

HazardActive는 두 조건이 모두 맞아야 true다: 2라운드 이상이고, 현재 주기가 작동 시작 시간인 4초 이상이다. `&&`는 “그리고”이며 앞 조건이 false면 뒤 조건은 평가하지 않는다.

```csharp
private bool InHazard(float x, float y, float radius) =>
    Math.Abs(x - 450) < 44 + radius ||
    (round == 3 && Math.Abs(y - 330) < 34 + radius);
```

InHazard는 세 값을 전달받아 위험 영역에 닿았는지 돌려주는 함수다. Abs는 절댓값이다. 중심 X=450에서 얼마나 떨어졌는지를 양수로 계산한다. 세로 띠의 반너비 44에 캐릭터 반지름을 더하므로 몸 가장자리만 닿아도 판정할 수 있다.

`||`는 “또는”이다. 세로 띠에 닿거나, 3라운드에서 가로 띠에 닿으면 true다. 이 함수 자체는 전기가 켜졌는지 검사하지 않는다. UpdateHazard가 먼저 HazardActive를 확인한다.

예: x=500, 반지름=18이면 |500-450|=50이고 44+18=62이므로 세로 띠에 닿는다. 정확히 62 떨어지면 `<` 조건이 false다.

### 18-10. AddEffect: 화면 효과 하나 등록하기

```csharp
private void AddEffect(string sheet, float x, float y,
    float size, float duration, float angle = 0)
{
    if (effects.Count >= 64) effects.RemoveAt(0);
    effects.Add(new GameEffect(sheet, x, y, size, duration, angle));
}
```

void는 돌려주는 값이 없다는 뜻이다. 매개변수는 호출자가 넘기는 정보다. sheet는 사용할 이미지 시트 이름, x/y는 위치, size는 출력 크기, duration은 재생 시간, angle은 회전 각도다.

`angle = 0`은 생략 가능한 기본 인수다. 호출할 때 앞의 다섯 값만 주면 각도는 0으로 사용한다.

Count는 목록 개수다. 이미 64개 이상이면 0번, 즉 가장 먼저 들어온 효과를 지운 뒤 새 효과를 추가한다. 이 함수는 그림을 즉시 그리지 않고 “나중에 Render가 그릴 목록”에 등록한다.

### 18-11. UpdateEffects: 끝난 효과와 점수 글자 지우기

```csharp
for (int i = effects.Count - 1; i >= 0; i--)
{
    effects[i].Update(dt);
    if (effects[i].Finished) effects.RemoveAt(i);
}
```

for의 괄호는 시작값; 반복 조건; 반복 후 처리 순서다. 목록 3개면 마지막 인덱스는 2다. i=2,1,0 순서로 처리하고 -1이 되면 끝난다. 빈 목록이면 시작이 -1이므로 한 번도 반복하지 않는다.

`effects[i]`는 i번째 효과다. Update(dt)는 그 효과의 경과 시간을 늘린다. Finished가 true면 목록에서 제거한다. 뒤에서부터 지우는 이유는 삭제로 앞당겨진 항목을 건너뛰지 않기 위해서다.

다음 for문도 같은 구조로 scorePopups를 처리한다. 팝업 Update는 글자를 위로 이동시키고 Life를 줄인다. Life가 0 이하이면 지운다. 여기서는 실제 score를 변경하지 않는다.

### 18-12. RemoveDefeatedEnemies: 죽은 적 정리하기

이 함수 역시 목록 뒤에서 앞으로 확인한다.

```csharp
if (enemies[i].Hp > 0) continue;
```

살아 있으면 이번 반복만 건너뛴다. 함수 전체를 끝내는 return과 다르다. Hp가 0 이하인 적은 아래 네 작업을 순서대로 수행한다.

1. 해당 적 위치에 파괴 효과를 등록한다.
2. `assets?.QueueSound("enemy_break")`로 파괴음을 예약한다. assets가 null이면 호출을 생략한다.
3. AddScore로 처치 점수와 점수 글자를 등록한다.
4. enemies.RemoveAt(i)로 적을 목록에서 제거한다.

제거 전에 X/Y를 읽어야 어느 위치에 효과를 낼지 알 수 있다. 적을 없애도 effects 목록에 등록한 그림은 자기 재생 시간이 끝날 때까지 남는다.

### 18-13. Initialize: 게임 시작 때 한 번 준비하기

`protected override void Initialize()`에서 protected는 이 클래스와 파생 클래스에서 접근한다는 뜻이다. override는 부모가 정한 초기화 함수를 이 게임에 맞게 구현한다는 뜻이다.

순서대로 배경 지우기 색을 정하고, 흰색 붓을 만들고, GameAssets와 GameHud를 만들고, 현재 상태를 로비로 설정한다. Initialize에서는 바로 전투를 시작하지 않는다. Enter가 들어와야 StartGame이 호출된다.

그래픽 붓을 필드 선언 시 만들지 않는 이유는 그래픽 장치가 준비된 시점에 만들어야 하기 때문이다.

### 18-14. StartGame: 새 도전 시작하기

```csharp
assets?.StopSounds();
player = new Player();
score = 0;
round = 0;
StartRound();
```

기존 효과음을 정리하고 새 플레이어 객체를 만든다. Player의 초기값으로 체력 등도 새로 설정된다. 점수와 라운드를 0으로 만들고 StartRound를 호출한다.

round=0인데 왜 0라운드가 아닌가? StartRound 첫 줄에서 round++하기 때문에 실제로는 1라운드가 시작된다.

bestScore는 여기서 0으로 만들지 않으므로 이번 실행 최고 기록은 남는다. 음악 선택도 새 게임을 시작한다고 강제로 켜지지 않는다.

### 18-15. StartRound: 다음 라운드 배치하기

함수의 코드를 위에서 아래로 다음 묶음으로 읽자.

1. round를 1 증가시키고 상태를 Playing으로 설정한다.
2. 전투 시간은 0, 준비 시간은 1.5초로 설정한다.
3. 이전 회복량·보너스·팝업·클리어 연출·전기 시작 기록을 초기화한다.
4. 플레이어를 (310,320)에 두고 쿨다운·무적 시간을 0으로 설정한다.
5. 바라보는 방향을 (1,0), 즉 오른쪽으로 설정한다.
6. 이전 적·이펙트·전기 피격 명단을 비운다.
7. 킥 효과·걷기 시간·이동 여부를 초기화한다.
8. 라운드에 맞는 적들을 만든다.

```csharp
player.KickCooldown = player.InvincibleTime = 0;
```

오른쪽부터 읽으면 InvincibleTime에 0을 넣고 KickCooldown에도 0을 넣는 것이다. 두 줄로 나누어 각각 0을 대입한 것과 같은 효과다.

```csharp
int count = GameRules.EnemyCount(round);
for (int i = 0; i < count; i++)
{
    float angle = MathF.Tau * i / count;
    enemies.Add(new Enemy(450 + MathF.Cos(angle) * 330,
                          330 + MathF.Sin(angle) * 190));
}
```

count는 6,8,10이다. Tau는 원 한 바퀴의 라디안인 2π다. 한 바퀴를 적 수만큼 똑같이 나눈 각도를 계산한다. Cos는 가로 방향, Sin은 세로 방향 위치를 정한다. 가로 반지름 330, 세로 반지름 190이므로 원이 아니라 타원 둘레다.

i=0이면 angle=0, cos=1, sin=0이므로 첫 적은 (780,330)에 생긴다. new Enemy가 적 하나를 만들고 Add가 목록에 넣는다.

**확인:** 이 함수에는 player.Hp=5와 score=0이 없다. 따라서 다음 라운드로 갈 때 체력·점수를 유지한다.

### 18-16. Update 앞부분: 지금 입력과 진행을 처리해도 되는가

Update는 파일의 중심이다. 매 프레임 다시 호출되며, 한 번의 호출에서는 그 프레임에 해당하는 처리만 한다.

```csharp
if (Form.ActiveForm == null)
{
    assets?.StopSounds();
    assets?.UpdateMusic(false);
    Input.Reset();
    return;
}
```

게임 창이 활성 상태가 아니면 소리를 멈추고 입력 기록을 비운 뒤 이번 Update를 끝낸다. 이 return이 있기 때문에 아래의 이동·전투 시간 증가도 실행되지 않는다. Render 호출 여부까지 이 return이 직접 바꾸는 것은 아니다.

```csharp
float dt = Math.Min((float)DeltaTime, 0.05f);
```

부모가 측정한 DeltaTime을 float로 변환한다. Min은 두 값 중 작은 값을 고르므로 한 프레임에 최대 0.05초만 반영한다. 프레임 지연 후 갑자기 큰 거리를 이동하는 현상을 줄인다.

### 18-17. Update 메뉴 입력: 음악·일시정지·로비

M을 처음 누르면 `musicEnabled = !musicEnabled`로 true/false를 뒤집는다. 누르고 있는 동안 매 프레임 뒤집지 않도록 IsKeyDown을 사용한다.

Esc 조건의 if/else if/else는 한 갈래만 실행한다.

- Playing이면 Paused로 바꾼다.
- Paused이면 Playing으로 바꾼다.
- 나머지 상태에서는 Lobby로 바꾼다.

그다음 `state == Paused && L 키`이면 로비로 바꾼다. L만 전투 중에 눌렀을 때는 로비로 가지 않는다.

일시정지 입력을 “Paused면 return”보다 먼저 검사해야 Esc로 다시 전투에 돌아갈 수 있다.

### 18-18. Update의 시각 시간과 상태별 return

Paused가 아니면 visualTime을 늘리고 UpdateEffects를 호출한다. 그래서 로비 미리보기나 결과 뒤의 이펙트도 재생된다. 정비 또는 승리 결과라면 clearTime도 늘린다.

`musicEnabled && state != Paused`가 true일 때만 음악 재생을 요청한다. 사용자가 음악을 끈 상태에서는 재개해도 자동으로 켜지지 않는다.

```csharp
bool enter = Input.IsKeyDown(Keys.Enter) && !IsHeld(Keys.Menu);
```

Keys.Menu는 여기서 Alt 키다. Enter를 처음 눌렀고 Alt는 누르지 않았을 때 enter=true다. 전체 화면 단축키 Alt+Enter가 게임 시작으로도 처리되는 일을 막는다.

상태별로 다음과 같이 함수가 일찍 끝난다.

| 분기 | 처리 | return 이유 |
| --- | --- | --- |
| Lobby / Result | Enter면 새 게임, 예약 효과음 재생 | 그 프레임에는 아래 전투 처리를 하지 않음 |
| Paused | 바로 종료 | 전투를 정지시킴 |
| RoundClear | Enter면 다음 라운드 | 정비 상태에서 적을 움직이지 않음 |
| readyTime > 0 | 준비 시간만 감소 | 준비 중 전투 시간·적·플레이어를 멈춤 |

StartGame이 상태를 Playing으로 바꿔도 Lobby 분기 안으로 이미 들어온 그 프레임은 마지막 return으로 끝난다. 다음 Update부터 새 상태를 기준으로 분기한다.

### 18-19. Update 마지막: 전투 한 프레임의 처리 순서

앞의 return들을 모두 통과해야 이 부분이 실행된다.

```text
roundTime 증가
→ 킥 쿨다운 / 무적 시간 / 킥 효과 시간 감소
→ 적 걷기 시간 증가
→ MovePlayer(dt)
→ J 키라면 Kick()
→ MoveEnemies(dt)
→ CheckEnemyCollisions()
→ UpdateHazard()
→ RemoveDefeatedEnemies()
→ CheckRoundEnd()
→ FlushSounds(TotalTime)
```

`Math.Max(0, 시간-dt)`는 시간이 음수가 되지 않게 한다. 쿨다운 0.01에서 dt=0.03을 빼면 -0.02지만 결과는 0이다.

플레이어 이동 후 Kick을 하므로 같은 프레임에 방향키와 J를 누르면 갱신한 방향으로 킥한다. 피해 처리 후 죽은 적을 제거하고, 제거 후 남은 적 수로 라운드 완료를 검사한다. 효과음은 여러 사건에서 예약한 뒤 마지막에 모아서 처리한다.

### 18-20. CheckRoundEnd: 패배·클리어·기록

Playing이 아니면 즉시 return하여 중복 보상을 막는다.

첫 번째 조건은 player.Hp<=0이다. 맞으면 Result로 바꾸고 게임 오버 소리를 예약한다. 다음 조건은 else if이므로 동시에 적이 0이어도 클리어 처리는 실행하지 않는다.

적이 0이면 다음 순서로 계산한다.

```csharp
healthBonus = player.Hp * 50;
roundBonus = 300 + GameRules.TimeBonus(roundTime) + healthBonus;
score += roundBonus;
```

예를 들어 전투 12.9초·체력 3이면 시간 보너스 480, 체력 보너스 150, 합계 930이다. 원래 score=600이었다면 1530이 된다.

마지막 라운드는 Result로 간다. 마지막이 아니면 RoundClear로 바꾸고 이전 체력을 저장한 뒤 최대 체력 안에서 1 회복한다. `recoveredHp = 회복 후 - 회복 전`이므로 체력 5에서는 0이다.

마지막 줄 `bestScore = Math.Max(bestScore, score)`는 둘 중 큰 점수를 기록한다. 전투 도중에도 이 함수가 호출되므로 최고 기록이 갱신된다.

### 18-21. UpdateHazard: 전기의 실제 피해 처리

전기가 꺼져 있으면 이미 맞은 적 집합을 비우고 wasHazardActive=false로 바꾼 뒤 종료한다. 다음 작동 때 새로 피해를 줄 준비다.

전기가 켜졌고 wasHazardActive=false면 “이번에 막 켜졌다”는 뜻이다. true로 바꾸고 효과음과 세로 6개의 스파크를 등록한다. 3라운드에서는 가로 10개도 추가한다. 다음 프레임에는 이 시작 연출을 반복하지 않는다.

플레이어 피해에는 세 조건이 필요하다: 위험 영역 안, 무적 시간 0 이하, 아직 살아 있음. 맞으면 체력 1 감소, 무적 1초, 소리·스파크 발생이다.

적 foreach에서는 죽음 → 영역 밖 → 이미 맞음 순서로 제외한다. 통과한 적은 집합에 기록하고 체력을 1 줄인다. 한 적이 십자 교차점에 있어도 이 함수에서 한 번만 처리된다.

**시험 함정:** 플레이어는 1초 무적으로 피해를 제한하고 적은 작동 주기별 집합으로 제한한다. 둘의 방식이 같지 않다.

### 18-22. IsHeld: 키를 누르고 있는지 확인하는 보조 함수

```csharp
return Input.IsKeyDown(key) || Input.IsKeyPress(key);
```

처음 누른 순간이거나 계속 누르고 있으면 true를 반환한다. 이동은 첫 프레임부터 움직여야 하므로 둘 다 확인한다. 공격은 누르고 있기만 해서 반복되지 않도록 Kick 호출에서 IsKeyDown만 검사한다.

반환 형식 bool에 맞춰 true/false를 돌려준다. `IsHeld(Keys.D)`의 결과를 if에서 바로 사용할 수 있다.

### 18-23. MovePlayer: 키 입력을 실제 위치 변화로 바꾸기

previousX/Y는 이동 전 좌표를 잠시 기억하는 지역 변수다. 함수가 다시 호출될 때마다 새로 현재 위치를 저장한다. 클래스 필드와 달리 이 함수 안에서만 사용한다.

dx,dy는 처음 0이다. W/위쪽이면 dy에서 1을 빼고, S/아래쪽이면 더한다. A/왼쪽은 dx에서 빼고, D/오른쪽은 더한다. 서로 반대 키를 같이 누르면 상쇄된다. W와 위쪽 키를 함께 눌러도 하나의 `||` 조건이므로 -2가 아니라 -1이다.

```csharp
float length = MathF.Sqrt(dx * dx + dy * dy);
```

Sqrt는 제곱근이다. (1,1)의 길이는 √2, (0,0)의 길이는 0이다. 길이가 양수일 때만 dx,dy를 길이로 나누어 정규화한다. 정규화는 방향은 유지하고 길이를 1로 만드는 것이다.

방향을 player.DirectionX/Y에 저장하고 `방향 × 속도 × dt`를 위치에 더한다. 예: 오른쪽, 속도 240, dt=0.05면 X가 12 늘어난다.

Math.Clamp는 범위 안으로 제한한다. 플레이어 반지름이 18이면 X 허용 범위는 48~852, Y는 108~552다.

마지막으로 이동 전후 거리가 0.001보다 큰지 검사하여 실제 이동 여부를 구한다. 벽을 향해 계속 키를 눌러도 위치가 바뀌지 않으면 걷기로 표시하지 않는다. 이동 중이면 걷기 시간을 늘리고 아니면 0으로 만든다.

### 18-24. Kick: 공격 가능 여부와 적중 판정

쿨다운이 남았으면 바로 종료한다. 공격 가능하면 쿨다운을 0.4초, 자세 표시 시간을 0.12초로 설정한다. 이 둘은 다른 시간이다: 자세가 끝나도 바로 다시 공격할 수 있는 것은 아니다.

Atan2(DirectionY, DirectionX)는 방향을 회전 각도로 바꾼다. 이 각도를 저장하므로 킥 표시 도중 방향키를 바꿔도 이미 시작한 궤적의 방향이 갑자기 바뀌지 않는다.

공격 중심은 플레이어 좌표에서 방향으로 42만큼 앞이다. (310,320)에서 오른쪽으로 차면 (352,320)이다. 각 살아 있는 적에 대해 중심 거리 < 38+적 반지름인지 확인한다.

맞으면 타격 효과, 금속음, 적 체력 -1, LaunchEnemy 호출을 한다. foreach를 끝까지 돌기 때문에 범위 안에 여러 적이 있으면 한 번에 여러 적을 찰 수 있다. Kick에서 직접 적을 목록에서 삭제하지는 않는다.

### 18-25. LaunchEnemy: 날아갈 속도를 저장하기

```csharp
enemy.VelocityX = dx * GameRules.LaunchSpeed;
enemy.VelocityY = dy * GameRules.LaunchSpeed;
enemy.FlyTime = GameRules.FlyDuration;
enemy.HitEnemies.Clear();
```

방향에 속도 600을 곱한다. 오른쪽이면 (600,0), 위쪽이면 (0,-600)이다. FlyTime은 0.65초다. 이전 공격의 피격 명단을 지워 새 공격에서 다시 상대를 때릴 수 있게 한다.

Enemy는 참조 형식이므로 매개변수 enemy를 통해 필드를 바꾸면 호출자가 가지고 있던 그 적 객체가 바뀐다. 적 복사본만 수정하는 것이 아니다.

### 18-26. MoveEnemies 앞부분: 날아가는 적

foreach로 모든 적을 확인하되 Hp<=0이면 건너뛴다. FlyTime>0이면 날아가기 처리, 아니면 추적 처리로 나뉜다.

날아가기에서는 남은 시간을 줄이고 속도×dt를 좌표에 더한 뒤 속도를 감속시킨다. 초기 VelocityX=600, dt=0.02면 이번 이동량은 12이고 그 후 속도는 600×exp(-0.04)로 줄어든다.

조건문에 들어올 때 FlyTime이 양수였다면 감소 후 0이 되어도 이 프레임은 날아가기 갈래를 끝까지 처리한다. 다음 프레임부터 추적 갈래로 들어간다.

### 18-27. MoveEnemies 중간: 벽 충돌

적의 중심이 벽에서 반지름만큼 안쪽인 경계를 넘어갔는지 네 방향 중 하나라도 확인한다.

wallX/Y는 벽 효과 위치, wallAngle은 벽을 향한 회전 각도다. 왼쪽→오른쪽→위쪽→아래쪽 순서의 if/else if로 충돌한 방향을 고른다. 모서리에서 두 방향을 동시에 넘으면 먼저 맞는 갈래가 선택된다.

벽 효과와 소리를 낸 뒤 적 체력을 1 줄이고 FlyTime=0으로 끝낸다. 마지막 Clamp가 적을 다시 경기장 안에 둔다. 벽을 뚫고 나가거나 벽에 날아가는 상태로 계속 박혀 피해를 반복하는 것을 줄인다.

### 18-28. MoveEnemies 뒷부분: 플레이어 추적과 접촉 피해

플레이어 위치에서 적 위치를 빼면 적→플레이어 방향이 된다. 거리가 0보다 클 때 그 거리로 나누어 정규화한 뒤 속도 `(55 + round * 10)`과 dt를 곱한다. 라운드별 속도는 65,75,85다.

이동 후 두 중심 거리 < 두 반지름 합인지 검사한다. 플레이어가 무적이 아니고 살아 있을 때만 체력 1을 줄이고 1초 무적을 준다. 적이 여러 대 겹쳐 있어도 먼저 맞은 뒤에는 무적 시간이 설정되어 같은 프레임의 뒤쪽 적에게 계속 맞지 않는다.

이 접촉 검사가 추적 갈래 안에 있으므로 날아가는 적은 플레이어에게 접촉 피해를 주지 않는다. 날아가기·추적 갈래가 끝나면 모두 Clamp로 경기장 안에 제한한다.

### 18-29. CheckEnemyCollisions: 날아가는 적이 다른 적을 때리기

바깥 반복문의 flying은 공격하는 날아가는 적, 안쪽 target은 맞을 후보 적이다. 죽었거나 날아가지 않는 flying은 제외한다. target이 자기 자신이거나 죽었거나 이미 맞은 상대면 제외한다.

충돌하면 flying.HitEnemies에 target을 기록하고 타격 효과·소리·target 체력 -1을 처리한다.

```csharp
float speed = MathF.Sqrt(flying.VelocityX * flying.VelocityX
                      + flying.VelocityY * flying.VelocityY);
```

속도 벡터의 길이를 구한다. 0보다 크면 각 성분을 speed로 나누어 방향만 얻고 LaunchEnemy로 target도 날린다. 예를 들어 속도 (300,400)의 길이는 500이고 방향은 (0.6,0.8)이다. LaunchEnemy가 방향에 600을 곱해 target의 새 속도는 (360,480)이 된다.

`target.HitEnemies.Add(flying)`은 방금 부딪힌 적에게 바로 역으로 피해를 주는 것을 막는다. 마지막으로 연쇄 점수 50을 더한다.

현재 코드는 목록 순서대로 즉시 속도를 바꾸므로 뒤에 있는 target은 같은 프레임에 다음 flying으로 처리될 수도 있다. 연쇄가 반드시 한 프레임 뒤에만 일어나는 것은 아니다. 정확한 추적 문제에서는 목록 순서도 확인해야 한다.

### 18-30. AddScore: 실제 점수와 표시 효과 함께 만들기

points를 score에 더한다. 팝업 목록이 24개 이상이면 가장 오래된 것을 지우고 새 ScorePopup을 만든다. reason은 “처치”나 “연쇄” 같은 설명이다.

이 함수의 x,y는 팝업 위치일 뿐 실제 점수 계산에는 영향이 없다. ScorePopup을 지워도 여기서 더한 score는 유지된다. 적 처치는 100, 연쇄 충돌은 50이며 라운드 완료 보너스는 CheckRoundEnd에서 별도로 더한다.

### 18-31. Distance: 두 점 사이 거리

```csharp
float dx = x2 - x1;
float dy = y2 - y1;
return MathF.Sqrt(dx * dx + dy * dy);
```

가로 차이와 세로 차이를 각각 제곱하여 더하고 제곱근을 구한다. 예: (0,0)과 (3,4)의 거리는 √(9+16)=5이다. 차이가 음수여도 제곱하므로 거리 자체는 음수가 되지 않는다.

반환 형식 float에 맞는 거리 값을 return한다. 다른 함수에서는 `Distance(...) < 기준`처럼 결과를 바로 비교할 수 있다.

### 18-32. Render 앞부분: 배경과 화면 분기

Render는 현재 상태를 그리는 함수다. brush/assets/hud 중 하나라도 null이면 출력할 준비가 안 됐으므로 return한다.

바닥 이미지 → 경기장 테두리 순서로 그린다. 로비 상태이면 DrawLobby를 호출하고 끝낸다. 로비가 아니면 전기 바닥, 번개 선, 상단 상태창, 라운드 정보를 그린다.

배율 유지와 중앙 정렬은 부모 G2AppBase.Render2D에서 이미 설정했다. 이 함수는 900×620 게임 좌표를 그대로 사용한다. 전체 화면 크기에 맞춰 개별 좌표를 다시 곱하면 중복 확대가 될 수 있다.

### 18-33. Render의 적 출력: 상태마다 다른 그림

`bool flying = enemy.FlyTime > 0`으로 날아가는 상태를 판단한다. 날아가면 속도 방향으로, 아니면 플레이어를 바라보는 방향으로 Atan2를 계산한다.

- 날아가면 enemy_flying 한 장을 사용한다.
- 전투 중이고 플레이어와 거리가 1보다 크면 걷기 시트의 한 칸을 사용한다.
- 그 밖에는 enemy_basic을 사용한다.

`(int)(enemyWalkTime * 7) % 4`는 초당 약 7번 바뀌는 0,1,2,3 프레임을 만든다. 0.5초면 (int)3.5=3, 1초면 7%4=3이다. 적 전체가 같은 enemyWalkTime을 사용하므로 걷기 타이밍이 공유된다. 마지막으로 적 체력 막대를 그린다.

### 18-34. Render의 플레이어 출력: 킥·걷기·무적 깜빡임

킥 효과 시간이 남았으면 저장한 kickAngle을 사용하고 아니면 마지막 이동 방향을 각도로 바꾼다.

```csharp
float opacity = player.InvincibleTime > 0 &&
    (int)(player.InvincibleTime * 12) % 2 == 0 ? 0.35f : 1;
```

무적 시간에 일정 간격으로 투명도를 0.35와 1 사이에서 바꾼다. 0은 완전 투명, 1은 완전 불투명이다. 화면이 깜빡이는 것은 무적의 표시이고 실제 피해 방지는 Update의 InvincibleTime 조건이 담당한다.

킥 표시가 우선이며, 그다음 실제 이동 중인 경우 걷기 시트, 그 밖에는 기본 자세를 그린다. 플레이어 걷기는 초당 약 9프레임으로 4칸을 반복한다. 킥 중에는 kickX/Y에 별도 궤적 이미지도 그린다.

### 18-35. Render 마지막: 효과와 패널을 겹쳐 그리기

먼저 effects의 모든 프레임, 그다음 scorePopups의 글자를 그린다. 이후 상태에 맞는 준비·정비·일시정지·결과 패널을 그린다. 정비 또는 승리 결과에서는 마지막에 클리어 불꽃을 그린다.

뒤에 그린 것이 앞에 보인다. 따라서 일시정지 패널은 전투 화면 위에 덮이고, 축하 불꽃은 패널 위로 보인다. 그림 출력과 달리 적의 체력·점수 계산은 여기서 하지 않는다.

### 18-36. DrawElectricArcs: 경고 테두리와 번개 선

붓이 없거나 1라운드이면 종료한다. 전기가 꺼져 있을 때는 2.5초 이상인 경고 구간에만 노란 테두리를 그리고 종료한다.

경고 색의 마지막 값 `0.45 + 0.4 * Sin(...)`은 투명도다. Sin 값은 -1~1이므로 약 0.05~0.85 범위로 변해 점멸한다.

작동 중에는 `tick = (int)(roundTime * 20)`으로 정수 시간을 만든다. 초당 약 20번 tick이 바뀐다. 18번 반복하며 y는 일정하게 증가시키고 x는 Sin으로 좌우 흔들리게 하여 다음 점까지 선을 잇는다. 3라운드에서는 가로 선도 만든다.

`new Vector2(x,y)`는 점 하나를 표현한다. DrawLine은 시작점·끝점·붓·두께를 받는다. 이 함수는 번개 그림만 그리며 피해는 UpdateHazard에 있다.

### 18-37. DrawCelebration: 36개의 축하 불꽃

clearTime이 2.6초를 넘으면 종료한다. 0~35의 i로 36개 점을 만든다.

| 계산 | 역할 |
| --- | --- |
| `i % 4 * 0.1f` | 점마다 0~0.3초 시작 지연 |
| `Math.Max(0, clearTime - 지연)` | 아직 시작 전이면 시간 0 |
| `i * 2.39996f` | 점들이 서로 다른 방향으로 퍼지게 하는 각도 |
| `90 + i % 7 * 24` | 여러 속도를 반복해서 부여 |
| `Cos(angle) * t * speed` | 가로로 퍼지는 이동 |
| `Sin(angle) * t * speed` | 세로로 퍼지는 이동 |
| `65 * t * t` | 시간이 갈수록 더 아래로 떨어지는 효과 |
| `2 + i % 3` | 반지름 2,3,4를 반복 |
| `Max(0, 1 - t/2.6)` | 시간이 지날수록 투명해짐 |

복잡해 보여도 기본은 “중심 좌표 + 시간에 따른 이동량”이다. 위치를 매번 계산해 작은 원을 그린다. 이 불꽃은 적이나 플레이어와 충돌하지 않는다.

### 18-38. FillCircle: 원 그리기 도우미

붓이 null이면 종료하고, 전달받은 color로 붓 색을 바꾼다. Ellipse는 중심 좌표와 가로·세로 반지름을 받는다. 두 반지름에 같은 radius를 넣어 원으로 그린다. FillEllipse는 테두리만 그리는 것이 아니라 안쪽도 채운다.

여러 곳에서 긴 원 그리기 코드를 반복하지 않도록 함수로 묶은 예다.

### 18-39. Rgb: 익숙한 색 숫자를 그래픽용 숫자로 변환

```csharp
return new Color4(red / 255f, green / 255f, blue / 255f, 1);
```

우리가 보통 사용하는 RGB는 0~255, 이 그래픽 API는 0~1을 쓴다. 255로 나누어 범위를 바꾼다. Rgb(255,128,0)은 대략 (1,0.502,0,1)이다. 마지막 1은 불투명도다.

255가 아니라 255f인 이유는 소수 나눗셈을 보장하기 위해서다. int끼리 128/255를 계산하면 0이 되어 색이 잘못 나온다. static은 특정 GameMain 객체의 필드를 읽지 않고 전달값만으로 계산한다는 설계에 맞는다.

### 18-40. Dispose: 종료할 때 자원 정리하기

hud, assets, brush 순서로 Dispose를 호출하고 참조를 null로 바꾼다. `?.` 덕분에 만들어지지 않은 자원은 건너뛴다. null을 대입하는 것 자체가 그래픽 자원을 해제하는 것은 아니므로 먼저 Dispose를 호출한다.

마지막 `base.Dispose()`는 부모 G2AppBase의 정리 함수를 호출한다. 자식이 쓰던 이미지·붓 등을 먼저 해제하고 그 자원이 의존하던 부모의 그래픽·오디오 장치를 나중에 해제한다.

Program의 using GameMain 구문 때문에 정상적으로 게임 실행을 마치면 이 함수가 호출된다.

### 18-41. 한 장면을 코드 전체로 연결해 보기

**상황: 준비 시간이 끝난 1라운드에서 오른쪽 이동과 J를 함께 누른다.**

1. 부모가 입력 상태와 DeltaTime을 준비한다.
2. Update가 상태·준비 시간 검사를 통과한다.
3. MovePlayer가 오른쪽 방향을 저장하고 X를 증가시킨다.
4. Kick이 새 위치 앞 42에 판정 원을 만들고 적의 체력을 줄인다.
5. LaunchEnemy가 적 속도와 날아가기 시간을 저장한다.
6. MoveEnemies가 적을 날리고, 벽을 넘으면 추가 피해를 준다.
7. CheckEnemyCollisions가 다른 적과의 연쇄 충돌을 검사한다.
8. 1라운드의 UpdateHazard는 작동하지 않고 끝난다.
9. RemoveDefeatedEnemies가 죽은 적에 파괴 효과·처치 점수를 주고 제거한다.
10. CheckRoundEnd가 패배나 라운드 완료 여부를 판정한다.
11. FlushSounds가 그 프레임의 효과음을 처리한다.
12. Render가 변경된 위치·체력·점수·효과를 그린다.

함수 하나를 공부한 뒤 “누가 호출하고, 무엇을 읽고, 어떤 값을 바꾸고, 누가 그 결과를 쓰는가”를 네 문장으로 설명하면 전체 연결을 이해하기 쉽다.

## 19. Player.cs 처음부터 끝까지 — 플레이어가 기억하는 정보

이 장은 `src/ActionGame/Player.cs`의 실제 코드 순서대로 설명한다. Player는 위치·체력 등을 보관하고, GameMain은 그 값을 읽고 바꾸면서 게임을 진행한다. 따라서 **Player에 이동 함수가 없어도 게임에서 플레이어가 움직일 수 있다.**

### 19-01. namespace와 주석: 소속과 역할 확인

```csharp
namespace ActionGame
{
    // 플레이어의 정보만 보관하는 클래스이다.
    // 실제 이동과 공격 처리는 GameMain에서 한다.
```

namespace는 형식의 소속을 묶는 이름 공간이다. GameMain과 Player가 모두 ActionGame 안에 있으므로 서로의 형식을 쉽게 사용할 수 있다.

`//`부터 그 줄 끝까지는 사람이 읽는 주석이다. 컴퓨터가 게임 동작으로 실행하지 않는다. 여기 주석은 “정보 저장은 Player, 움직임과 공격 처리는 GameMain”이라는 역할 분담을 설명한다.

### 19-02. public class Player: 설계도 만들기

```csharp
public class Player
{
```

class는 객체를 만들 설계도를 선언한다. public은 다른 코드에서도 이 형식에 접근할 수 있게 한다. 이 선언만으로 화면에 캐릭터가 생기지는 않는다. GameMain에서 `new Player()`로 객체를 만들고 Render에서 그 객체의 좌표를 읽어 이미지를 그린다.

이 클래스에는 명시적인 부모 클래스 선언이 없다. GameMain처럼 G2AppBase를 상속하는 클래스는 아니며, C# 클래스의 기본 부모인 object를 가진다.

### 19-03. public float X = 450: 가로 위치

```csharp
public float X = 450;
```

| 부분 | 뜻 |
| --- | --- |
| public | GameMain 등 다른 클래스가 읽고 바꿀 수 있다 |
| float | 소수를 담을 수 있는 숫자 형식 |
| X | 필드 이름 |
| = 450 | 객체가 만들어질 때 넣는 초기값 |
| ; | 문장의 끝 |

필드는 객체가 가지고 있는 변수다. `player.X`는 player가 가리키는 플레이어 객체의 X 필드에 접근한다는 뜻이다.

왜 int가 아니라 float인가? 이동량은 속도×dt로 계산하므로 3.84처럼 소수가 될 수 있기 때문이다. 초기값 450은 정수 리터럴이지만 float에 대입할 수 있다. 소수 리터럴을 float로 쓰려면 보통 `450.5f`처럼 f를 붙인다.

**현재 게임에서 꼭 구분할 점:** `new Player()` 직후 X는 450이지만, GameMain.StartRound가 X=310으로 바꾼다. 따라서 실제 전투 시작 위치는 X=310이다. 이 초기값 하나만 보고 전투 시작 위치를 답하면 틀릴 수 있다.

### 19-04. public float Y = 320: 세로 위치

```csharp
public float Y = 320;
```

Y도 소수를 사용할 수 있는 좌표다. 화면에서는 왼쪽 위가 기준이고 아래로 갈수록 Y가 커진다.

- X 증가: 오른쪽으로 이동.
- X 감소: 왼쪽으로 이동.
- Y 증가: 아래로 이동.
- Y 감소: 위로 이동.

`(X,Y)=(450,320)`은 중심 위치를 나타낸다. StartRound에서는 `(310,320)`으로 배치한다. 전체 화면에서도 이 게임 좌표는 그대로이며, 실제 화면에 맞춘 확대는 부모 프레임워크가 처리한다.

### 19-05. public float Radius = 18: 충돌용 몸 크기

```csharp
public float Radius = 18;
```

Radius는 반지름이다. 플레이어의 충돌 모양을 반지름 18짜리 원으로 생각한다. 지름은 36이다.

적과의 중심 거리 < 플레이어 반지름 + 적 반지름이면 접촉으로 처리한다. 둘 다 18이므로 중심 거리가 36보다 작으면 닿은 것이다. 정확히 36이면 현재 `<` 조건은 false다.

Radius는 그림 파일의 크기와 같지 않다. GameMain.Render에서는 플레이어 이미지를 50 크기로 그리지만, 충돌 반지름은 18이다. 이미지의 투명 여백과 모양 때문에 그리는 크기와 판정 크기를 따로 정한다.

이 값은 벽 밖으로 나가지 않도록 좌표를 제한할 때와 전기 바닥에 몸이 닿았는지 확인할 때도 사용한다.

### 19-06. public float Speed = 240: 초당 이동 거리

```csharp
public float Speed = 240; // 1초에 이동하는 픽셀 수
```

Speed는 현재 위치가 아니라 이동 속도의 크기다. 코드의 240은 게임 좌표 기준으로 1초에 이동할 거리이며, 전체 화면에서 물리적인 화면 픽셀 이동량은 출력 배율에 따라 달라진다.

GameMain.MovePlayer가 다음과 같이 사용한다.

```csharp
player.X += dx * player.Speed * dt;
player.Y += dy * player.Speed * dt;
```

오른쪽 dx=1, dy=0, dt=0.05라면 X에 12를 더하고 Y는 그대로 둔다. 시작 X=310이면 X=322가 된다.

Speed 값만 저장한다고 자동으로 움직이지 않는다. MovePlayer가 입력 방향과 dt를 곱해 X/Y에 반영해야 실제로 움직인다.

### 19-07. public int Hp = GameRules.MaxHp: 체력

```csharp
public int Hp = GameRules.MaxHp;
```

Hp는 체력이다. 현재 게임은 체력이 정수 단위로 줄고 늘어나므로 int를 사용한다. GameRules.MaxHp는 현재 5인 상수다. 초기 체력을 다른 파일의 공통 규칙에서 가져온다.

`Hp` 자체가 상수인 것은 아니다. 초기값을 상수에서 읽었을 뿐이므로 플레이 중에는 바꿀 수 있다.

```csharp
player.Hp -= 1; // 예: 5 → 4
```

Hp가 0 이하인지 GameMain.CheckRoundEnd가 검사해 게임 오버를 결정한다. Player가 스스로 결과 화면으로 바꾸지는 않는다.

다음 라운드에서는 같은 Player 객체를 유지하면서 최대 5 안에서 1 회복한다. 새 게임에서는 `player = new Player()`로 객체를 새로 만들어 초기 체력을 다시 적용한다.

### 19-08. DirectionX와 DirectionY: 마지막으로 바라본 방향

```csharp
// 마지막으로 이동한 방향을 기억해서 그 방향으로 발차기한다.
public float DirectionX = 1;
public float DirectionY = 0;
```

방향은 위치와 다르다. `(1,0)`은 “X=1,Y=0에 서 있다”가 아니라 “오른쪽을 향한다”는 뜻이다.

| 방향 | DirectionX | DirectionY |
| --- | --- | --- |
| 오른쪽 | 1 | 0 |
| 왼쪽 | -1 | 0 |
| 위쪽 | 0 | -1 |
| 아래쪽 | 0 | 1 |
| 오른쪽 위 | 약 0.707 | 약 -0.707 |

대각선 값이 1,-1 그대로가 아닌 이유는 GameMain.MovePlayer에서 방향 길이를 1로 맞추기 때문이다. 그래야 대각선 이동도 같은 속도다.

이동 입력이 있을 때 방향을 저장하고, 키를 떼었다고 0으로 지우지 않는다. 그래서 멈춘 뒤 J를 눌러도 마지막 방향으로 공격한다. 단, 새 라운드가 시작하면 StartRound가 (1,0)으로 다시 설정한다.

Kick에서 공격 위치는 다음처럼 계산한다.

```csharp
kickX = player.X + player.DirectionX * 42;
kickY = player.Y + player.DirectionY * 42;
```

플레이어가 (310,320), 방향이 (1,0)이면 킥 중심은 (352,320)이다. Atan2로 방향을 각도로 바꾸어 캐릭터 이미지도 회전시킨다.

### 19-09. KickCooldown: 다음 공격까지 남은 시간

```csharp
public float KickCooldown = 0;
```

Cooldown은 재사용 대기시간이다. 값이 0이면 기다릴 시간이 없다는 뜻이다. 처음에는 0이므로 준비 시간이 끝난 뒤 바로 공격할 수 있다.

공격할 때 GameMain.Kick은 먼저 `KickCooldown > 0`이면 return한다. 공격이 가능하면 GameRules.KickCooldown의 값인 0.4를 넣는다. 전투 Update는 매 프레임 dt만큼 빼서 0까지 줄인다.

| 시점 | 값 예시 |
| --- | --- |
| 공격 전 | 0 |
| 공격 직후 | 0.4 |
| 전투 시간이 0.1초 더 지난 뒤 | 약 0.3 |
| 충분히 지난 뒤 | 0 |

계산에는 `Math.Max(0, KickCooldown-dt)`를 쓰므로 음수로 내려가지 않는다. 0.02에서 dt=0.05를 빼도 최종값은 0이다.

**이름이 같아도 다른 것:** `GameRules.KickCooldown`은 고정된 설정값 0.4이고, `player.KickCooldown`은 계속 줄어드는 남은 시간이다. J를 계속 누르고 있어도 대기시간이 끝나자마자 자동 공격하는 것은 아니다. 현재 Kick 호출은 키를 새로 누른 순간만 검사한다.

### 19-10. InvincibleTime: 피해를 다시 받을 때까지의 보호 시간

```csharp
public float InvincibleTime = 0;
```

Invincible은 무적이라는 뜻이다. 적이나 전기에 맞으면 GameMain이 이 값을 1로 설정한다. 값이 양수인 동안 피해 조건을 통과하지 못하므로 추가 피해를 받지 않는다. 전투 Update에서 dt만큼 줄어들어 0이 되면 다시 맞을 수 있다.

예: 체력 5인 상태에서 맞으면 체력 4, 무적 시간 1이 된다. 다른 적이 같은 프레임에 겹쳐 있어도 무적 시간이 이미 양수라 추가 피해를 막는다.

화면의 깜빡임은 Render에서 이 값을 읽어 투명도를 바꾸는 표현이다. **깜빡여서 무적이 되는 것이 아니라, 무적 상태를 보여 주기 위해 깜빡이는 것이다.**

KickCooldown과 InvincibleTime은 각각 공격 제한과 피해 제한이라는 별개의 값이다. 무적이라고 발차기가 금지되는 규칙은 없다. 일시정지 중에는 전투 Update까지 내려가지 않으므로 두 값 모두 줄어들지 않는다.

### 19-11. 끝의 중괄호와 보이지 않는 기본 생성자

파일 끝의 첫 `}`는 Player 클래스 범위, 다음 `}`는 ActionGame 이름 공간 범위를 끝낸다.

Player에는 직접 작성한 생성자가 없다. 생성자를 하나도 선언하지 않은 클래스에는 컴파일러가 매개변수 없는 기본 생성자를 제공하므로 `new Player()`를 사용할 수 있다. 객체를 만드는 과정에서 각 필드에 작성된 초기값도 적용된다.

초보자용 이해 예시:

```csharp
Player first = new Player();
Player second = new Player();
first.Hp = 2;
```

각각 new를 사용했으므로 서로 다른 객체다. first.Hp는 2, second.Hp는 5다. 반면 `Player second = first;`라고 하면 두 변수가 같은 객체를 가리켜 체력 변경도 공유한다.

### 19-12. Player의 값을 누가 바꾸고 누가 읽는가

| 필드 | 주로 바꾸는 곳 | 주로 읽는 곳 |
| --- | --- | --- |
| X, Y | StartRound, MovePlayer | Render, Kick, 적 추적·충돌 |
| Radius | 선언의 초기값, 현재 플레이 중에는 변경하지 않음 | MovePlayer, MoveEnemies, UpdateHazard |
| Speed | 선언의 초기값, 현재 플레이 중에는 변경하지 않음 | MovePlayer |
| Hp | 피해 처리, CheckRoundEnd의 정비 회복 | CheckRoundEnd, GameHud |
| DirectionX/Y | StartRound, MovePlayer | Kick, Render |
| KickCooldown | StartRound, Kick, Update | Kick, GameHud |
| InvincibleTime | StartRound, 피해 처리, Update | 피해 조건, Render |

이렇게 정보를 가진 객체와 규칙을 처리하는 함수를 연결하면 필드가 왜 필요한지 알 수 있다.

### 19-13. Player 전체 상황 추적

```text
new Player()
→ X=450, Y=320, Hp=5, 방향=(1,0), 대기시간=0, 무적시간=0
StartRound()
→ X=310, Y=320, 오른쪽을 향하도록 재설정
준비 시간이 끝난 뒤 D 키로 dt=0.05만큼 이동
→ X=322, Y=320, 방향=(1,0)
J 키로 공격
→ KickCooldown=0.4, 킥 중심=(364,320)
적에게 피격 (무적이 아니었다고 가정)
→ Hp=4, InvincibleTime=1
```

한 필드가 바뀌어도 다른 모든 필드가 자동으로 바뀌는 것은 아니다. 어떤 함수를 통과했고 그 함수가 어디에 대입했는지 따라가야 한다.

### 19-14. Player 복습 문제와 답

| 질문 | 답 |
| --- | --- |
| Player에 Move 함수가 없는데 어떻게 이동하는가? | GameMain.MovePlayer가 player.X/Y를 변경한다. |
| X의 초기값은 450인데 전투 시작은 왜 310인가? | StartRound가 X를 310으로 덮어쓴다. |
| 좌표에 float를 사용하는 이유는? | dt에 따른 소수 이동량을 반영하기 위해서다. |
| Radius=18이면 지름은? | 36. |
| 이미지 크기 50과 충돌 지름 36이 꼭 같아야 하는가? | 아니다. 그림과 판정은 따로 정한다. |

| 기본 생성자를 직접 안 써도 new Player()가 되는 이유는? | 생성자를 선언하지 않아 컴파일러가 매개변수 없는 생성자를 제공한다. |

## 20. Enemy.cs 처음부터 끝까지 — 적의 상태와 생성자

이 장은 `src/ActionGame/Enemy.cs`의 실제 순서대로 설명한다. Enemy도 상태를 저장하는 클래스이며, 추적·날아가기·피해 처리는 GameMain이 담당한다. Player와의 핵심 차이는 **적은 여러 객체가 있고, 생성할 때 위치를 받으며, 날아가는 속도와 충돌 기록을 가진다**는 것이다.

### 20-01. namespace, 주석, public class Enemy

```csharp
namespace ActionGame
{
    // 적마다 new Enemy로 별도 객체를 만든다. 한 적의 Hp를 바꿔도 다른 적의 Hp는 그대로다.
    public class Enemy
```

ActionGame 이름 공간 안에 Enemy 클래스를 선언한다. public으로 다른 코드에서 만들고 사용할 수 있다. 클래스 선언 자체는 적 한 대가 아니라 적을 만들 설계도다.

주석은 **각각 new로 만든 서로 다른 객체**에 대한 설명이다. 같은 객체를 여러 변수로 가리키면 상태가 공유된다는 점은 뒤의 참조 예제에서 구분한다.

### 20-02. X와 Y: 아직 위치가 지정되지 않은 필드

```csharp
public float X;
public float Y;
```

이름은 각각 가로·세로 위치다. Player와 달리 선언 줄에 `= 값`이 없다. 객체의 숫자 필드는 우선 기본값 0을 가지지만, Enemy 생성자에서 전달받은 좌표를 대입한다. 따라서 `new Enemy(150,180)`가 끝나면 X=150, Y=180이다.

“값을 안 적었으니 아무 숫자나 들어간다”는 뜻이 아니다. 또 이 설명은 객체의 필드에 대한 것이며, 초기화하지 않은 지역 변수를 읽어도 된다는 뜻이 아니다.

추적 중에는 GameMain.MoveEnemies가 X/Y를 변경한다. 날아가는 중에도 같은 필드를 사용하지만 이동량을 구하는 방식이 달라진다.

### 20-03. Radius: 적의 충돌 반지름

```csharp
public float Radius = 18;
```

반지름 18의 원으로 충돌을 판단한다. 적끼리는 반지름 합 36, 플레이어와도 현재 합 36, 킥 원과는 합 38+18=56을 사용한다.

GameMain.Render에서 적 이미지는 48 크기로 출력한다. 그림 크기 48과 판정 지름 36은 별개의 설정이다. Radius는 벽 제한과 전기 영역 접촉에도 사용된다.

### 20-04. Hp: 적마다 따로 가진 체력

```csharp
public int Hp = 2;
```

새 적의 초기 체력은 2다. 직접 킥, 벽 충돌, 다른 적에 의한 연쇄 충돌, 전기 피해에서 1씩 감소할 수 있다.

체력이 0 이하가 되어도 이 클래스가 스스로 사라지는 것은 아니다. GameMain.RemoveDefeatedEnemies가 적 목록에서 제거하고 파괴 효과와 점수를 처리한다. 목록에서 제거하는 것과 즉시 객체 메모리가 해제되는 것은 같은 말이 아니다. 다른 참조가 남아 있을 수도 있고, 관리 메모리 회수는 가비지 컬렉터가 담당한다.

예: Hp=2 → 킥으로 1 → 벽 충돌로 0 → 적 제거와 100점. 벽에 부딪히지 않으면 킥 한 번만으로 항상 죽는 것은 아니다.

### 20-05. VelocityX와 VelocityY: 날아가는 속도 성분

```csharp
public float VelocityX;
public float VelocityY;
```

Velocity는 방향이 포함된 속도다. X/Y가 “현재 어디에 있나”라면 VelocityX/Y는 “1초 동안 어느 방향으로 얼마나 움직이나”를 나타낸다. 두 필드의 초기값은 0이다.

| 속도 값 | 의미 |
| --- | --- |
| (600,0) | 오른쪽으로 날아감 |
| (-600,0) | 왼쪽으로 날아감 |
| (0,-600) | 위로 날아감 |
| (360,480) | 오른쪽 아래로 날아감, 전체 속도 크기는 600 |

GameMain.LaunchEnemy는 정규화된 방향에 LaunchSpeed=600을 곱해 저장한다. MoveEnemies는 다음 식으로 좌표를 바꾼다.

```csharp
enemy.X += enemy.VelocityX * dt;
enemy.Y += enemy.VelocityY * dt;
```

(150,180)에서 속도 (600,0), dt=0.02면 이동 후 (162,180)이다. 그 다음 속도에 감속 비율을 곱한다.

Enemy에 Player.Speed 같은 필드가 없는 이유도 살펴보자. 현재 적의 일반 추적 속도는 GameMain에서 `(55 + round * 10)`으로 계산하고, 이 두 Velocity 필드는 주로 날아가기 이동에 사용한다.

### 20-06. FlyTime: 날아가기 상태를 결정하는 남은 시간

```csharp
public float FlyTime = 0; // 0보다 크면 킥을 맞고 날아가는 중이다.
```

초기값 0은 현재 날아가는 중이 아니라는 뜻이다. LaunchEnemy가 이 값을 0.65로 설정한다. 직접 킥뿐 아니라 연쇄 충돌도 LaunchEnemy를 호출하므로 날아가는 상태가 될 수 있다.

MoveEnemies는 FlyTime>0이면 저장된 Velocity로 이동하고, 아니면 플레이어를 추적한다. 매 전투 프레임마다 FlyTime에서 dt를 빼되 0 아래로 내려가지 않게 한다. 벽에 부딪히면 시간이 남아 있어도 0으로 만들어 날아가기를 끝낸다.

**주의:** Velocity가 0이 아니라고 반드시 날아가는 중은 아니다. 현재 상태 판단의 기준은 FlyTime이다. 벽 충돌에서 FlyTime만 0으로 바꿔도 다음 프레임에는 추적 갈래로 간다. 남아 있는 속도 필드 값은 그 갈래에서 이동에 사용하지 않는다.

날아가는 적은 현재 코드에서 플레이어에게 접촉 피해를 주지 않는다. 이 규칙은 Enemy 클래스가 아니라 GameMain.MoveEnemies의 if/else 위치로 구현되어 있다.

### 20-07. HitEnemies 선언: 이미 부딪힌 상대를 기록하는 집합

```csharp
public HashSet<Enemy> HitEnemies = new HashSet<Enemy>();
```

이 줄이 Enemy에서 가장 낯설 수 있다. 부분별로 읽자.

| 부분 | 뜻 |
| --- | --- |
| public | GameMain에서 접근할 수 있음 |
| HashSet<Enemy> | Enemy 객체를 중복 없이 담는 집합 형식 |
| HitEnemies | 필드 이름, 이미 맞힌 적들의 기록 |
| new HashSet<Enemy>() | 내용이 비어 있는 집합을 새로 만듦 |

`<Enemy>`는 이 집합에 담는 항목의 형식이다. 이 줄이 새 적을 만들어 집합에 넣는 것은 아니다. **빈 집합 하나를 만드는 것**이다. 새로운 적마다 이 필드 초기화가 실행되므로 각 적은 자기만의 집합을 가진다.

HitEnemies의 항목 수를 `Count`로 읽고, `Add(상대)`로 기록하고, `Contains(상대)`로 들어 있는지 검사하고, `Clear()`로 기록을 비운다. List처럼 순서나 인덱스를 사용하기 위한 자료구조는 아니다.

### 20-08. 왜 HashSet이 필요한가

A가 B와 부딪혔는데 다음 프레임에도 두 원이 겹쳐 있을 수 있다. 매 프레임 피해를 주면 충돌 한 번이 여러 번 공격한 것처럼 처리된다.

GameMain.CheckEnemyCollisions는 대략 다음 순서로 처리한다.

```text
A가 날아가는지 확인
→ B가 자기 자신·죽은 적·이미 맞힌 적인지 확인
→ 겹쳤으면 A.HitEnemies에 B를 기록
→ B의 체력을 1 줄임
→ B도 날아가도록 설정
```

한 번 기록한 B는 A의 같은 날아가기 동안 다시 피해 대상으로 삼지 않는다. A를 다시 발로 차면 LaunchEnemy에서 A.HitEnemies.Clear()를 호출하므로 새로운 날아가기에서는 다시 B를 때릴 수 있다.

B가 새로 날아갈 때는 B.HitEnemies에 A도 넣는다. 방금 부딪힌 두 적이 즉시 서로를 다시 때리는 것을 막기 위한 처리다.

### 20-09. 같은 좌표와 같은 객체는 다르다

현재 Enemy는 Equals나 GetHashCode를 직접 재정의하지 않는다. 따라서 이 HashSet의 기본 비교에서는 같은 적 객체를 가리키는지를 기준으로 구분한다.

```csharp
Enemy a = new Enemy(150, 180);
Enemy b = new Enemy(150, 180);
Enemy c = b;
a.HitEnemies.Add(b);
a.HitEnemies.Add(c);
```

b와 c는 같은 객체를 가리키므로 두 번 Add해도 a.HitEnemies.Count는 1이다. a와 b는 좌표가 같지만 서로 다른 new로 만들었으므로 다른 객체다.

집합에 b를 넣은 뒤 b.X를 변경해도 다른 적이 되는 것은 아니다. 같은 객체의 위치만 달라진다. 이 기록은 좌표 목록이 아니라 **맞힌 상대 객체의 목록**이라는 점을 기억하자.

Enemy의 HitEnemies 필드는 public이고 readonly가 아니므로 외부 코드가 새 집합을 대입하는 것도 문법적으로 가능하다. 다만 현재 게임에서는 Add/Contains/Clear로 기존 집합을 사용한다.

### 20-10. public Enemy(float x, float y): 생성자 선언

```csharp
public Enemy(float x, float y)
```

생성자는 new로 객체를 만들 때 실행되는 특별한 코드다. 이름이 클래스 이름 Enemy와 같고, void를 포함한 반환 형식을 쓰지 않는다.

float x, float y는 호출자가 전달할 두 좌표를 받는 매개변수다. 예를 들어 `new Enemy(150,180)`이면 생성자 안에서 x는 150, y는 180이다. 정수 리터럴도 여기의 float 매개변수로 전달할 수 있다.

Player와 달리 Enemy는 이 생성자를 직접 선언했다. 따라서 컴파일러가 매개변수 없는 생성자를 자동으로 추가하지 않는다. 현재 코드에서 `new Enemy()`는 맞는 생성자가 없어 컴파일되지 않으며, 좌표 두 개를 주어야 한다.

### 20-11. X = x, Y = y: 매개변수를 객체 필드에 저장

```csharp
{
    X = x;
    Y = y;
}
```

C#은 대소문자를 구분한다. 대문자 X는 이 객체의 필드이고 소문자 x는 이번 생성자 호출에서 받은 매개변수다.

`X = x`는 오른쪽 x 값을 읽어 왼쪽 X에 저장한다. 반대로 `x = X`라고 쓰면 매개변수 쪽에 필드 값을 넣는 것으로 의미가 달라진다.

뜻을 더 분명하게 쓰면 다음과 같다.

```csharp
this.X = x;
this.Y = y;
```

this는 지금 만들고 있는 객체 자신이다. 현재 코드는 이름이 대소문자로 구분되므로 this를 생략해도 된다.

매개변수 x/y는 생성자가 끝나면 더 이상 그 이름으로 사용할 수 없지만, 복사해 둔 필드 X/Y는 객체 안에 남는다. float는 값 형식이므로 좌표 숫자 값을 복사한다.

### 20-12. 객체 하나가 만들어지는 과정을 따라가기

```csharp
Enemy enemy = new Enemy(700, 180);
```

초보자 관점에서 이 줄이 끝난 뒤의 결과를 아래처럼 정리할 수 있다.

| 필드 | 값 | 값이 정해진 근거 |
| --- | --- | --- |
| X | 700 | 생성자에서 x를 대입 |
| Y | 180 | 생성자에서 y를 대입 |
| Radius | 18 | 필드 초기값 |
| Hp | 2 | 필드 초기값 |
| VelocityX | 0 | 숫자 필드의 기본값 |
| VelocityY | 0 | 숫자 필드의 기본값 |
| FlyTime | 0 | 필드 초기값 |
| HitEnemies | 빈 집합, Count=0 | 필드에서 new HashSet 호출 |

여기까지는 적 객체를 만든 것이다. GameMain의 적 목록에 넣으려면 `enemies.Add(enemy)`도 필요하다. 현재 StartRound는 두 동작을 한 줄로 묶어 `enemies.Add(new Enemy(...))`로 작성했다.

### 20-13. Enemy 변수는 객체 자체가 아니라 참조를 담는다

```csharp
Enemy first = new Enemy(150, 180);
Enemy second = first;
second.Hp = 1;
```

new는 한 번뿐이다. second=first는 적 객체 전체를 복사해 만드는 것이 아니라 같은 객체를 가리키는 참조를 복사한다. 그래서 first.Hp로 읽어도 1이다.

반대로 다음은 서로 다른 적 두 대다.

```csharp
Enemy first = new Enemy(150, 180);
Enemy second = new Enemy(700, 180);
second.Hp = 1;
```

이번에는 first.Hp는 2, second.Hp는 1이다.

GameMain.LaunchEnemy(Enemy enemy, ...)에 적을 넘겼을 때 그 적의 필드가 실제로 바뀌는 이유도 같은 원리다. 매개변수에는 참조의 복사본이 전달되며, 복사된 참조가 같은 객체를 가리킨다. `ref` 없이도 객체의 필드 수정은 호출자에게 보인다. 다만 함수 안에서 매개변수 자체를 `enemy = new Enemy(...)`로 바꾸는 것은 호출자의 변수까지 새 객체로 바꾸는 것과 다르다.

### 20-14. 적 하나의 전투 흐름

```text
new Enemy(700,180)
→ Hp=2, FlyTime=0, 추적 가능한 상태
MoveEnemies
→ 플레이어 방향을 계산해 X/Y를 변경
킥 적중
→ Hp=1
LaunchEnemy
→ VelocityX/Y에 날아갈 속도 저장
→ FlyTime=0.65, HitEnemies.Clear()
다음 이동 처리
→ 속도×dt만큼 위치 변경, 감속, FlyTime 감소
벽 충돌
→ Hp=0, FlyTime=0
RemoveDefeatedEnemies
→ 파괴 효과, 처치 점수, enemies에서 제거
```

각 단계는 상황에 따라 같은 Update 안에서 이어질 수도 있다. GameMain.Update가 Kick 다음에 MoveEnemies를 호출하므로 킥을 맞은 프레임에 바로 날아갈 수 있다.

적이 벽에 닿지 않으면 날아가는 시간이 끝난 뒤 살아 있는 상태로 추적을 다시 시작할 수 있다. 전기나 연쇄 충돌 때문에 먼저 죽는 경우도 있다.

### 20-15. Enemy의 필드와 GameMain 연결

| 필드 | 주로 바꾸는 곳 | 사용 목적 |
| --- | --- | --- |
| X, Y | 생성자, MoveEnemies | 위치 출력·추적·충돌 |
| Radius | 필드 초기값 | 원 충돌·벽 제한·전기 접촉 |
| Hp | Kick, MoveEnemies, CheckEnemyCollisions, UpdateHazard | 생존 판단·체력 표시 |
| VelocityX/Y | LaunchEnemy, MoveEnemies의 감속 | 날아가기 이동·연쇄 방향·이미지 회전 |
| FlyTime | LaunchEnemy, MoveEnemies | 추적과 날아가기 갈래 선택 |
| HitEnemies | LaunchEnemy, CheckEnemyCollisions | 같은 공격에서의 중복 충돌 방지 |

Enemy.HitEnemies는 “이 적이 날아가며 맞힌 상대”, GameMain.shockedEnemies는 “이번 전기 작동으로 피해를 받은 적”이다. 둘 다 HashSet<Enemy>이지만 저장하는 의미와 비우는 시점이 다르다.

## 21. GameHud.cs 처음부터 끝까지 — 상태를 화면에 보여 주기

이 장은 `src/ActionGame/GameHud.cs`의 선언·함수 순서대로 읽는다. HUD는 플레이 중 체력·점수 같은 정보를 겹쳐 보여 주는 화면을 뜻한다. 이 프로젝트의 GameHud는 로비·정비·결과 화면도 담당한다.

**핵심 구분:** GameMain은 점수·체력·상태를 바꾸고, GameHud는 전달받은 값을 표시한다. “Enter 다시 도전”을 그리는 함수가 Enter 입력까지 처리하는 것은 아니다.

### 21-01. using과 namespace

```csharp
using System.Numerics;
using Vortice.Direct2D1;
using Vortice.DirectWrite;
using Vortice.Mathematics;
```

Direct2D1은 도형과 붓, DirectWrite는 글꼴 굵기·정렬, Mathematics는 Rect와 Color4 같은 형식을 사용하기 위한 이름 공간이다. 현재 GameHud에서 System.Numerics의 형식은 직접 사용하지 않는다. using이 있다고 그 기능을 반드시 사용하는 것은 아니다.

namespace ActionGame은 게임 클래스의 소속이다. 이후의 중괄호 안에 GameHud가 들어간다.

### 21-02. internal sealed class GameHud : IDisposable

```csharp
internal sealed class GameHud : IDisposable
```

| 부분 | 뜻 |
| --- | --- |
| internal | 같은 어셈블리 안에서 접근할 수 있음 |
| class | 객체를 만들 클래스 선언 |
| sealed | 다른 클래스가 이 클래스를 상속하지 못하게 함 |
| GameHud | 클래스 이름 |
| : IDisposable | IDisposable 인터페이스를 구현함 |

여기의 콜론은 GameMain : G2AppBase와 달리 **인터페이스 구현**이다. IDisposable은 자원을 정리하는 Dispose 함수를 제공한다는 약속이다. 인터페이스가 대신 자원을 정리해 주는 것은 아니므로 아래에서 직접 구현한다.

### 21-03. brush: 도형을 그릴 붓

```csharp
private readonly ID2D1SolidColorBrush brush;
```

GameHud 내부에서 사용할 단색 붓이다. 생성자에서 값을 넣고 이후 다른 붓으로 재대입하지 않도록 readonly를 쓴다. readonly여도 `brush.Color = color`처럼 그 객체의 속성은 변경할 수 있다. “참조를 바꾸지 못함”과 “객체 내부를 바꾸지 못함”은 다르다.

붓은 Box에서 사각형을 칠할 때 재사용한다. 사각형마다 새 붓을 만들지 않는다.

### 21-04. 글꼴 필드 일곱 개: 역할별 크기와 정렬

```csharp
private readonly G2Font small = new("맑은 고딕", 11, FontWeight.Bold);
private readonly G2Font body = new("맑은 고딕", 14, FontWeight.Normal);
```

`new(...)`는 왼쪽 형식이 G2Font이므로 `new G2Font(...)`로 이해하면 된다. 인수는 글꼴 이름·크기·굵기 순서다. GameHud 객체를 만들 때 준비하고 그릴 때 재사용한다.

| 필드 | 크기 | 굵기·정렬 | 쓰임 |
| --- | --- | --- | --- |
| small | 11 | 굵게, 기본 왼쪽 정렬 | 작은 항목 이름 |
| body | 14 | 보통, 기본 왼쪽 정렬 | 설명 문구 |
| keyFont | 12 | 굵게, 가운데 | 키 모양 안의 글자 |
| number | 22 | 굵게, 기본 왼쪽 정렬 | 상태창 숫자 |
| centered | 16 | 굵게, 가운데 | 중앙 안내 |
| resultTitle | 32 | 맑은 고딕, 굵게, 가운데 | 큰 제목 |
| resultNumber | 40 | 굵게, 가운데 | 최종 점수 |

`textAlignment: TextAlignment.Center`는 **이름 있는 인수**다. G2Font 생성자의 textAlignment라는 매개변수에 값을 전달한다. 다른 선택 매개변수를 기본값으로 두면서 특정 설정만 지정할 수 있다.

가운데 정렬은 전체 화면의 중앙이 아니라, DrawText에 넘긴 **글자 배치 사각형 안에서 가로 가운데**라는 뜻이다. 세로 정렬까지 자동으로 가운데가 되는 것은 아니다.

### 21-05. C 함수와 공통 색상

```csharp
private static Color4 C(int r, int g, int b, float a = 1)
    => new(r / 255f, g / 255f, b / 255f, a);
```

코드를 짧게 쓴 색상 변환 함수다. 0~255의 RGB를 0~1로 바꾸고 a는 투명도로 전달한다. a를 생략하면 기본값 1, 즉 완전 불투명이다.

예를 들어 C(255,128,0,0.5f)는 대략 (1,0.502,0,0.5)다. 255f로 나누므로 정수 나눗셈으로 소수가 사라지지 않는다.

다음 두 선언 줄은 Cyan·Gold·Muted·White·Red 색을 한 번 정한다. static이므로 클래스에서 공유하고 readonly이므로 초기화 후 재대입하지 않는다. 주의·보상·일반 설명 등의 색을 이름으로 사용하면 숫자를 매번 외울 필요가 없다.

### 21-06. Target 속성: 현재 그리기 장치 가져오기

```csharp
private ID2D1HwndRenderTarget Target => G2AppBase.Instance!.RenderTarget;
```

Target을 읽을 때 현재 실행 중인 게임의 RenderTarget을 돌려준다. 새 장치를 만드는 코드가 아니다.

여기의 `!`는 “개발자는 이 값이 null이 아니라고 판단한다”는 컴파일러용 표시다. `!조건`이라는 논리 부정과 다르다. 런타임에서 null을 고쳐 주지 않으므로 게임 장치가 준비된 뒤 GameHud를 만들어야 한다. 현재 GameMain.Initialize가 그 순서를 보장한다.

### 21-07. 생성자 GameHud: 준비된 장치로 붓 만들기

```csharp
public GameHud() => brush = Target.CreateSolidColorBrush(White);
```

new GameHud() 때 실행되는 생성자다. White 색을 가진 붓을 생성해 brush에 저장한다. 생성자에는 반환 형식이 없다. `=>`를 풀면 중괄호 안에서 같은 대입문을 실행하는 형태가 된다.

### 21-08. Box: 사각형을 칠하는 공통 함수

```csharp
private void Box(float x, float y, float w, float h, Color4 color)
{
    brush.Color = color;
    Target.FillRectangle(new Rect(x, y, w, h), brush);
}
```

매개변수는 왼쪽 X·위쪽 Y·너비·높이·색이다. Rect의 마지막 두 값은 오른쪽 끝·아래쪽 끝이 아니다. Box(10,20,100,30,색)는 오른쪽 110, 아래쪽 50까지의 사각형을 채운다.

이 함수는 배경 가림막, 진행 막대, 키 모양을 그릴 때 반복 사용된다. 색을 바꾸고 같은 붓을 재사용한다.

### 21-09. Text: 그림자와 외곽선을 넣은 글자

Text의 매개변수는 글꼴 객체, 문자열, 배치 위치와 크기, 색이다.

```csharp
bool display = font == resultTitle || font == resultNumber || font == number;
```

이 비교는 전달된 글꼴이 지정한 큰 글꼴 객체 중 하나인지 확인한다. 문자열 내용이 제목인지 자동으로 분석하는 것이 아니다. 해당 객체를 사용한 글자에만 외곽선을 넣는다.

큰 글꼴이면 다음 순서로 그린다.

1. resultTitle이면 외곽선 거리 1.5, 나머지는 0.8을 선택한다.
2. (x+2,y+3)에 어두운 글자를 그려 그림자를 만든다.
3. for문 8회로 원 둘레 8방향에 어두운 글자를 그린다.
4. 마지막에 원래 위치에 요청한 색으로 글자를 그린다.

`angle = i * PI / 4`는 45도 간격이다. Cos와 Sin에 edge를 곱해 아주 조금씩 다른 방향으로 이동한 위치를 만든다. 큰 글자는 그림자 1회+외곽선 8회+본 글자 1회, 총 10번 DrawText를 호출한다. 일반 글꼴은 마지막 1회만 실행한다.

마지막 글자를 나중에 그리기 때문에 앞서 그린 어두운 글자의 가장자리만 보여 외곽선처럼 보인다. Text는 화면 출력만 하며 점수를 계산하지 않는다.

### 21-10. DrawStatus 앞부분: 철판·로고·체력

assets, player, score, remaining을 전달받아 플레이 중의 상태창을 그린다. assets는 이미지를 그릴 도구, player는 실제 플레이어 상태다.

처음에 DrawHud로 철판을 그리고 DrawTitle로 로고를 올린다. 다음에 Hp<=2인지 계산해 위험 문구와 색을 바꾼다.

```csharp
for (int i = 0; i < GameRules.MaxHp; i++)
    assets.DrawSprite(i < player.Hp ? "hp_full" : "hp_empty",
        254 + i * 29, 52, 28);
```

최대 체력 5라면 i=0~4를 반복한다. 체력 3이면 i=0,1,2는 채운 아이콘, i=3,4는 빈 아이콘이다. X는 254,283,312,341,370으로 29 간격이다. DrawSprite의 x/y는 이미지 중심으로 사용한다는 점이 Box의 왼쪽 위 좌표와 다르다.

### 21-11. DrawStatus 중간: 공격 가능 표시와 충전 막대

ready는 KickCooldown<=0인지 판단한 bool이다. 이에 따라 아이콘·문구·색을 바꾼다. 이것은 화면 표시이고 실제 공격 제한은 GameMain.Kick이 판단한다.

```csharp
95 * Math.Clamp(1 - player.KickCooldown / GameRules.KickCooldown, 0, 1)
```

최대 너비 95에 준비된 비율을 곱한다.

| 남은 쿨다운 | 계산 결과 | 막대 너비 |
| --- | --- | --- |
| 0.4 | 1-0.4/0.4=0 | 0 |
| 0.2 | 1-0.2/0.4=0.5 | 47.5 |
| 0 | 1-0/0.4=1 | 95 |

Clamp는 비율을 0~1 안으로 제한한다. 먼저 어두운 바탕 막대를 그리고 그 위에 금색 막대를 올린다. 설정 쿨다운은 현재 0.4로 0보다 크다는 전제다. 이 계산에 사용하는 분모를 임의로 0으로 바꾸면 안 된다.

### 21-12. DrawStatus 뒷부분: 숫자와 키 안내

score.ToString("N0")는 점수를 소수 없이 자릿수를 구분한 문자열로 만든다. 한국어 환경에서는 12345가 보통 12,345로 표시된다. 실제 점수 int는 그대로다.

### 21-13. DrawEnemyHealth: 적 위의 작은 체력 막대

적 중심 x/y를 기준으로 (x-15,y-32)에 어두운 바탕을 그린다. 그 위에 2칸을 반복해 표시한다.

중첩 조건식을 순서대로 읽자. “이 칸이 남은 체력인가?”가 false면 어두운 색이다. true면 “적이 날아가는가?”에 따라 금색 또는 빨간색을 고른다.

### 21-14. DrawResult: 성공·실패 결과 화면

먼저 화면 전체에 투명도 0.82의 어두운 사각형을 덮고 결과 철판 이미지를 그린다. 뒤의 전투 화면이 희미하게 남는 이유는 완전 불투명으로 덮지 않았기 때문이다.

accent는 처음 Gold, lost가 true면 Red로 바꾼다. lost에 따라 제목도 “작전 중단/작전 성공”, “다시 일어설 시간/폐기장 정리 완료”로 달라진다.

최종 점수, 도달 구역, 남은 에너지, 이번 실행 최고 기록을 전달받아 출력하고 재도전·로비 키 안내를 그린다. 이 함수에서 승패를 새로 판정하거나 최고 점수를 저장하지 않는다. GameMain이 이미 판정한 결과를 보여 준다.

### 21-15. DrawStagePreview: 실제 전투가 아닌 움직이는 미리보기

x/y는 미리보기 왼쪽 위 기준점이다. 바닥을 245×140으로 그리고 그 안에 각 이미지를 기준점+상대 위치로 배치한다. 기준점을 바꾸면 전체 미리보기의 위치를 옮기기 쉽다.

2구역 이상이면 전기 타일을 세로 4개, 3구역이면 가로 7개도 그린다. `2+(int)(time*10)%2`는 방전 프레임 2와 3을 교대로 선택한다. 이 미리보기에서는 실제 전투의 대기·경고 주기를 그대로 재현하지 않고 작동 모습만 보여 준다.

`cycle = time % 2`는 0~2 미만의 시간을 반복한다. 적 그림의 X에 cycle*18을 더하므로 오른쪽으로 움직이다가 2초마다 처음 위치로 돌아간다. 실제 Enemy 객체의 X를 바꾸는 것이 아니다.

킥 궤적의 투명도는 0.55+0.35×Sin으로 약 0.2~0.9 사이에서 변한다. 타격 그림은 4프레임을 반복한다. 체력·점수·충돌은 전혀 처리하지 않는 연출이다.

### 21-16. DrawLobby: 세 구역을 같은 형식으로 배치

화면을 어둡게 하고 로고와 제목을 그린다. for문은 i=0,1,2로 세 장의 카드를 만든다.

```csharp
float x = 55 + i * 267;
DrawStagePreview(assets, i + 1, x + 5, 211, time + i * 0.3f);
```

카드 기준 X는 55,322,589다. 배열 인덱스처럼 반복 번호는 0부터지만 구역 번호는 1부터라서 i+1을 전달한다. 시간에도 i*0.3을 더해 카드의 애니메이션이 모두 똑같은 순간에 움직이지 않게 한다.

### 21-17. DrawRound 앞부분: 구역 이름과 시간 표시

상단 안쪽의 어두운 바를 그리고 round를 두 자리, GameRules.RoundName으로 이름을 출력한다.

```csharp
$"{(int)time / 60:00}:{(int)time % 60:00}"
```

time=125.9라면 (int)time은 125다. 정수 나눗셈 125/60은 2, 나머지 125%60은 5다. `:00`으로 두 자리를 채워 02:05가 된다. 이 표시를 만든다고 실제 time 필드의 소수 값이 없어지는 것은 아니다.

### 21-18. DrawRound 중간: 전기 상태·남은 시간

phase=time%6으로 주기 안의 시간을 계산한다. 1구역이면 기본 문구 “목표 · 모든 적 처치”를 유지한다. 2구역 이상이면 다음 순서로 분기한다.

1. phase>=4: 작동 중이며 종료까지 6-phase초, 청록색.
2. 그 밖에 phase>=2.5: 경고이며 작동까지 4-phase초, 금색.
3. 그 밖: 충전 중이며 작동까지 4-phase초.

예: phase=4.6이면 약 1.4초 후 작동 종료다. `:0.0`은 소수 한 자리 표시다. 이는 계산값을 포맷하는 것이고 별도의 타이머를 만드는 것이 아니다.

음악 켜짐/꺼짐 문구는 전달받은 musicEnabled 설정을 보여 준다. 오디오 장치가 실제로 소리를 내고 있다는 검증 결과까지 의미하지는 않는다.

### 21-19. DrawRound 마지막: 처치 진행률

```csharp
float progress = 1 - (float)remaining / GameRules.EnemyCount(round);
```

전체 중 남은 비율을 1에서 빼면 처치한 비율이다. 8대 중 2대가 남으면 1-2/8=0.75, 막대 너비는 824×0.75=618이다.

(float)를 빼면 두 int의 나눗셈이 먼저 실행되어 2/8이 0이 된다. 그러면 진행률이 1로 잘못 표시된다. “결과 변수만 float이면 나눗셈도 자동으로 소수가 된다”는 생각에 주의하자.

### 21-20. DrawRoundClear: 실제 계산 결과를 보여 주는 정비 화면

배경을 어둡게 하고 큰 패널, 완료 구역 이름, 다음 구역 제목을 그린다. 플레이어 이미지와 크기가 34~40 사이로 변하는 체력 아이콘을 넣는다.

recovery는 기본 “에너지 가득”이고 recoveredHp>0이면 실제 회복량을 넣은 문자열로 바뀐다. 체력을 여기서 증가시키지는 않는다.

### 21-21. DrawPause: 정지 메뉴를 그리기

어두운 가림막과 철판을 그린 뒤 재개·음악·로비 키를 보여 준다. 음악이 켜져 있으면 “음악 끄기”, 꺼져 있으면 “음악 켜기”라고 쓴다. 현재 상태가 아니라 **누르면 수행할 행동**을 안내하는 문구다.

로비로 가면 도전이 종료된다는 설명도 출력한다. 이 함수 자체는 게임을 멈추지 않는다. GameMain.Update의 Paused 분기에서 이동·전투를 건너뛰고, Render가 이 함수를 호출해서 정지 화면을 표시한다.

### 21-22. DrawReady: 준비 시간 막대

가로로 긴 띠 위에 구역 번호·이름·작전 준비 문구를 그린다.

```csharp
300 * (1 - remaining / GameRules.ReadyDuration)
```

remaining이 1.5이면 너비 0, 0.75이면 150, 0이면 300이다. 시간이 지날수록 막대가 채워진다. 이 함수는 남은 시간을 줄이지 않는다. GameMain.Update에서 줄인 값을 받아 그린다.

### 21-23. DrawScorePopup: 떠오르는 점수 글자 출력

```csharp
float opacity = Math.Clamp(popup.Life / 0.4f, 0, 1);
```

초기 Life는 0.8이므로 초기 계산값 2가 Clamp로 1이 된다. 따라서 처음 0.4초 동안은 완전 불투명하고 마지막 0.4초 동안 서서히 흐려진다. Life=0.2이면 투명도 0.5다.

글자 박스 X를 popup.X-85, 너비를 170으로 지정해 가로 중심이 popup.X가 되게 한다. y-38은 대상 위에 띄우기 위한 위치 보정이다. 글자의 위쪽 이동과 수명 감소는 ScorePopup.Update, 여기서는 출력만 담당한다.

### 21-24. KeyHint: 클릭 기능 없는 키 모양 안내

key는 “Esc”, action은 “일시정지” 같은 문자열이다. x/y는 안내 위치, keyWidth는 키 상자의 너비다.

아래로 2만큼 내린 어두운 사각형을 먼저 그린 후 위에 밝은 사각형을 겹쳐 작은 그림자를 만든다. 그 위에 keyFont로 키 이름을 쓰고, x+keyWidth+10 위치에 설명을 쓴다.

긴 공백을 문자열에 넣어 정렬하는 대신 좌표로 분리하기 때문에 키 길이가 달라도 배치를 조절할 수 있다. 이 함수는 마우스 클릭이나 키 이벤트를 등록하지 않는다.

### 21-25. Dispose: 글꼴과 붓 정리

resultNumber부터 keyFont까지 일곱 글꼴과 brush를 각각 Dispose한다. GPU·그래픽 API와 연결된 자원을 사용이 끝난 시점에 해제하기 위한 처리다.

GameHud는 assets를 전달받아 사용하지만 소유해서 생성한 것이 아니므로 여기서 assets.Dispose를 호출하지 않는다. GameMain이 GameHud와 GameAssets를 각각 정리한다. 누가 만들고 누가 해제하는지 구분해야 한다.

현재 Dispose 구현은 “보통 한 번 호출한다”는 사용 흐름을 따른다. IDisposable을 구현했다고 모든 구현이 반복 호출을 자동으로 안전하게 처리하는 것은 아니다.

## 22. GameAssets.cs 처음부터 끝까지 — 이미지와 소리 관리

이 장은 `src/ActionGame/GameAssets.cs`의 실제 순서를 따른다. assets는 게임에 쓰이는 이미지·소리 같은 자원을 뜻한다. 이 클래스는 자원을 처음에 읽어 두고 이름으로 찾아 그리거나 재생하며 종료 시 정리한다.

### 22-01. using과 클래스 선언

System.Numerics는 Matrix3x2로 이미지 회전·이동 변환을 표현할 때, Vortice.Mathematics는 Rect와 Color4 등의 그래픽 형식에 사용한다.

```csharp
internal sealed class GameAssets : IDisposable
```

GameHud와 마찬가지로 같은 어셈블리 내부용이고 상속을 막은 클래스다. IDisposable을 구현해 이미지와 오디오 자원을 해제한다. GameMain.Initialize에서 new GameAssets를 호출한다.

### 22-02. images와 sounds: 이름으로 찾는 Dictionary

```csharp
private readonly Dictionary<string, G2Texture> images = new();
private readonly Dictionary<string, G2Audio> sounds = new();
```

Dictionary<TKey,TValue>는 키와 값을 짝지어 저장한다. 여기서 키는 string이고 값은 각각 이미지 또는 소리 객체다.

```text
images["player_idle"] → 플레이어 기본 이미지 객체
sounds["metal_hit"] → 금속 타격 소리 객체
```

이미지 파일을 매 프레임 다시 읽는 대신 한 번 만든 객체를 이름으로 꺼낸다. readonly는 Dictionary 객체의 재대입을 막지만 Add·Clear 등 내용 변경은 가능하다. `new()`는 왼쪽에 적힌 형식의 생성자를 호출하는 축약이다.

대괄호로 존재하지 않는 키를 직접 읽으면 예외가 날 수 있다. 현재 이미지 출력은 미리 등록한 이름을 정확히 사용한다는 전제다.

### 22-03. pendingSounds와 lastPlayed: 소리 중복 제어

```csharp
private readonly HashSet<string> pendingSounds = new();
private readonly Dictionary<string, double> lastPlayed = new();
```

pendingSounds는 다음 FlushSounds에서 재생을 검토할 효과음 이름의 집합이다. 같은 프레임에 metal_hit을 여러 번 넣어도 같은 문자열은 한 항목만 남는다. 집합이므로 요청 순서를 보장하는 재생 목록으로 생각하면 안 된다.

lastPlayed는 효과음 이름별 마지막 처리 시간을 저장한다. 예를 들어 metal_hit→10.0이라는 기록이 있으면, 곧이어 같은 소리를 재생하려 할 때 시간 차이를 확인할 수 있다. 시간은 TotalTime에 맞춰 double을 쓴다.

### 22-04. music와 SoundEnabled

```csharp
private G2Audio? music;
public bool SoundEnabled => sounds.Count > 0;
```

music은 BGM용 별도 오디오 객체다. 오디오 장치가 없거나 아직 만들지 않았으면 null일 수 있어서 ?를 붙인다.

SoundEnabled는 sounds에 효과음이 한 개 이상 들어 있는지 읽을 때 계산하는 속성이다. 음악 켜기/끄기 설정을 바꾸는 스위치가 아니다. “실제로 스피커에서 들리는 중”을 검사하는 속성도 아니다. 현재 GameMain의 musicEnabled 필드와 구분하자.

### 22-05. GameAssets 생성자와 try/catch

```csharp
public GameAssets()
{
    try
    {
        // 리소스 생성 코드
    }
    catch { Dispose(); throw; }
}
```

생성 중 파일 누락 등으로 예외가 발생하면 catch로 이동한다. 그 전에 일부 만들어 둔 자원은 Dispose로 정리하고 `throw;`로 원래 예외를 다시 전달한다.

실패를 숨기고 정상 작동한 것처럼 넘어가는 코드가 아니다. 일부만 로딩된 객체를 그대로 사용하지 않게 하면서 이미 확보한 자원도 정리하는 구조다. try/catch와 뒤에서 나오는 try/finally는 용도가 다르다.

### 22-06. 이미지 목록 foreach: 경로에서 이름과 파일 만들기

```csharp
foreach (string path in new[] { "player/player_idle", ... })
    images.Add(Path.GetFileName(path),
        new G2Texture(ResourcePath("image/" + path + ".png")));
```

설명용 `...`는 원본의 나머지 문자열 목록을 생략한 표시다. 실제 코드에는 이미지 19개의 이름이 모두 나열되어 있다.

new[]는 원소를 보고 배열 형식을 추론한다. 여기서는 문자열 배열이다. foreach가 경로 문자열 하나씩 path로 가져온다.

path가 player/player_idle일 때 단계별 결과는 다음과 같다.

1. Path.GetFileName(path) → `player_idle`이라는 Dictionary 키.
2. `"image/" + path + ".png"` → `image/player/player_idle.png`.
3. ResourcePath → 실행 파일 기준의 실제 파일 경로.
4. new G2Texture → 이미지 자원 생성.
5. images.Add → 이름과 객체를 Dictionary에 등록.

이 목록의 path에는 확장자가 없으므로 GetFileName 결과에도 .png가 없다. images.Add는 같은 키가 이미 있으면 덮어쓰지 않고 예외를 낸다. 따라서 다른 폴더에 있더라도 같은 파일 이름 키를 중복 등록하지 않도록 해야 한다.

### 22-07. 효과음과 배경음악 로딩

```csharp
if (G2AudioContext.Instance?.Audio != null)
```

오디오 장치가 있을 때만 효과음 8개와 BGM을 만든다. ?.는 Instance가 null이면 다음 멤버 접근을 생략한다. 조건이 false이면 소리 로딩을 건너뛰고 이미지로 게임을 실행할 수 있게 한다.

효과음은 sound/sfx 아래의 wav 파일을 sounds에 넣고, BGM scrapyard_loop.wav는 별도 music 필드에 넣는다. 소리 파일이 없거나 손상된 경우까지 전부 무시하는 것은 아니며, 장치가 있는 상태에서 로딩 예외가 나면 바깥 catch에서 처리한다.

`MasteringVoice?.SetVolume(0.65f)`는 전체 출력 음량을 0.65로 설정한다. 효과음만이 아니라 이 오디오 출력에 연결된 음악에도 영향을 준다.

### 22-08. ResourcePath: 실행 위치에 맞는 파일 경로

```csharp
Path.Combine(AppContext.BaseDirectory, "resource",
    relative.Replace('/', Path.DirectorySeparatorChar))
```

AppContext.BaseDirectory는 일반적으로 실행 파일이 있는 기본 경로다. 현재 터미널의 작업 폴더나 소스 프로젝트 경로를 뜻하는 것은 아니다. 뒤에 resource 폴더와 상대 경로를 결합한다.

예시: 기본 경로가 `.../bin/Debug/net9.0-windows/`이고 relative가 `sound/sfx/clear.wav`이면 그 출력 폴더의 resource 아래 소리 파일을 읽는다. csproj가 리소스를 빌드 결과 폴더로 복사하므로 연결된다.

Replace는 경로 구분자 `/`를 현재 환경의 구분자로 맞춘다. Path.Combine은 여러 경로 부분을 결합한다. 개인 PC의 절대 경로를 소스에 직접 박아 두지 않기 위한 구조다.

### 22-09. DrawFloor: 원본 영역을 출력 사각형에 그리기

```csharp
images["arena_floor"].Draw(destination, new Rect(0, 0, 840, 480));
```

destination은 게임 화면 어디에 얼마나 크게 그릴지, 두 번째 Rect는 원본 이미지에서 어느 부분을 사용할지다.

| 사각형 | 뜻 |
| --- | --- |

같은 원본 바닥을 전투에서는 840×480으로, 로비 미리보기에서는 245×140으로 그릴 수 있다. 원본 파일 자체를 매번 수정하는 것이 아니다.

### 22-10. DrawElectricTile: 2×2 전기 이미지의 한 칸

```csharp
new Rect((frame % 2) * 627, (frame / 2) * 627, 627, 627)
```

1254×1254 원본을 627×627 네 칸으로 나눈다. frame은 int이므로 frame/2는 정수 나눗셈이다.

### 22-11. DrawElectricFloor: 라운드에 따라 타일 깔기

1라운드이면 return한다. 그 외에는 phase=time%6을 계산하고 대기 0번, 경고 1번, 작동 중 2·3번 프레임을 선택한다.

### 22-12. DrawSprite 선언과 기본 매개변수

```csharp
public void DrawSprite(string name, float x, float y,
    float size, float angle = 0, float opacity = 1)
```

name은 등록된 이미지 키, x/y는 중심 기준 위치, size는 출력 크기, angle은 라디안 회전, opacity는 투명도다. angle과 opacity를 생략하면 회전 0, 불투명도 1이다.

`DrawSprite("hp_full",254,52,28)`처럼 호출하면 기본 인수를 쓴다. 이 함수는 현재 단일 자세·아이콘 이미지의 원본 크기 규칙에 맞춰 작성되었으며 임의의 모든 PNG 크기를 자동으로 알아내는 함수는 아니다.

### 22-13. DrawSprite의 Transform 저장과 회전·이동

```csharp
var target = G2AppBase.Instance!.RenderTarget;
Matrix3x2 saved = target.Transform;
```

var는 오른쪽 표현으로 형식을 컴파일 시 추론한다. 아무 형식이나 마음대로 바뀌는 변수라는 뜻은 아니다. saved는 기존 그리기 변환을 저장한다. Matrix3x2는 회전·확대·이동을 표현하는 숫자 묶음이며 값 형식이다.

```csharp
target.Transform = Matrix3x2.CreateRotation(angle)
    * Matrix3x2.CreateTranslation(x, y) * saved;
```

이 코드의 변환 순서는 이미지 자신의 원점 주변에서 회전 → 게임 좌표 x/y로 이동 → 기존 화면 배율과 여백 이동 적용이다. saved를 포함해야 전체 화면의 동일 비율 확대·중앙 정렬도 유지된다. 행렬을 곱하는 순서를 바꾸면 결과가 달라질 수 있다.

초보 단계에서는 행렬 원소를 전부 외우기보다 “회전할 중심을 먼저 정하고, 원하는 위치로 옮긴 뒤, 전체 화면 변환을 적용한다”는 흐름을 이해하자.

### 22-14. DrawSprite의 원본 크기와 중심 보정

sourceSize는 kick_arc이면 96, 그 외에는 64를 선택한다. 이는 현재 리소스 규격에 맞춘 것이다.

```csharp
new Rect(-size / 2 + offsetX, -size / 2, size, size)
```

이미지의 왼쪽 위를 -size/2로 두면 이미지 중심이 로컬 원점 (0,0)이 된다. 이후 회전·이동을 하므로 캐릭터가 자기 중심을 기준으로 돌아간다.

size=50이면 보통 (-25,-25)에서 50×50으로 그린다. player_kick은 offsetX=50×0.075=3.75를 더해 왼쪽 위 X가 -21.25가 된다. 공격 자세 그림의 투명 여백 차이를 보정하는 것이며, player.X나 충돌 중심 자체를 변경하지 않는다.

실제 이미지는 images[name]에서 가져오고, 출력 사각형·원본 사각형·opacity를 전달해 그린다.

### 22-15. DrawSprite의 finally: 다음 그림을 위해 변환 복구

```csharp
finally { target.Transform = saved; }
```

try 안에서 그림을 정상적으로 그렸든 예외가 발생했든, finally로 기존 변환을 복원한다. 예외를 잡아서 무시하는 catch가 아니며 예외는 필요하면 호출자에게 계속 전달된다.

복구하지 않으면 다음 적, 다음 UI도 직전 캐릭터의 회전·이동이 적용된 상태로 그려질 수 있다. 공유 장치의 임시 설정은 사용 후 되돌리는 원리다.

### 22-16. DrawTitle과 DrawPanel: 고정 원본을 쓰는 간단한 함수

DrawTitle은 title_logo 원본의 (0,0,2172,724)를 destination에 그린다. DrawPanel은 scrap_result 원본의 (0,0,1536,1024)를 사용한다.

둘 다 =>로 한 줄로 쓴 void 함수다. return값을 돌려주는 속성과 달리, 호출하면 Draw라는 작업을 한다. 해당 그림의 원본 크기를 호출자마다 반복해서 적지 않도록 감싼 함수다.

### 22-17. DrawHud: 철판 양 끝을 찌그러뜨리지 않기

```csharp
float cap = destination.Height * 240 / 724;
```

원본 HUD는 왼쪽 240, 가운데 1692, 오른쪽 240 픽셀로 나누어 그린다. 원본 높이 724에 맞춰 출력 높이에서 양 끝 너비 cap을 계산한다.

출력 높이 90이면 cap≈29.83이다. 출력 너비 880에서는 가운데 너비가 약 820.33이 된다.

1. 왼쪽: 출력 x부터 cap 너비, 원본 X=0~240.
2. 가운데: 출력 x+cap부터 전체 너비-2×cap, 원본 X=240부터 1692 너비.
3. 오른쪽: 출력 오른쪽-cap부터 cap 너비, 원본 X=1932부터 240 너비.

양 끝 볼트는 높이에 맞춘 비율을 유지하고 가운데 철판만 가로로 늘린다. UI 이미지의 부분을 나누어 늘리는 기법이다. 임의로 출력 너비를 너무 작게 주면 가운데 너비가 음수가 될 수 있으므로 현재 호출부처럼 충분한 너비를 사용해야 한다.

### 22-18. DrawFrame: 걷기·타격 시트 한 프레임

DrawSprite와 비슷하지만 sheet와 frame을 추가로 받아 2×2 시트에서 한 칸을 고른다. 우선 `Math.Clamp(frame,0,3)`으로 번호를 제한한다. -1이면 0, 5이면 3이다. `%4`처럼 처음부터 반복시키는 동작은 아니다.

Transform 저장·회전·이동·finally 복구는 DrawSprite와 같다. source는 다음 식으로 고른다.

```csharp
new Rect(frame % 2 * 128, frame / 2 * 128, 128, 128)
```

프레임 3은 원본 (128,128)에서 128×128을 읽는다. 전기 시트는 한 칸 627이므로 이 함수 대신 DrawElectricTile을 사용한다.

anchorX는 일반 효과 0.5, wall_hit_sheet 0.83이다. 일반 그림은 가운데를 기준으로, 벽 충돌 그림은 원본 안의 실제 접촉점이 위치한 곳을 기준으로 맞춘다. size=80인 벽 효과의 왼쪽 시작은 -66.4가 된다.

이 함수는 frame 번호를 계산하거나 시간을 늘리지 않는다. GameMain 또는 GameEffect가 번호를 정해 전달하고, 이 함수는 지정한 칸만 그린다.

### 22-19. QueueSound: 지금 재생하지 않고 요청만 등록

```csharp
public void QueueSound(string name) => pendingSounds.Add(name);
```

소리 이름을 집합에 추가한다. 같은 metal_hit이 한 프레임에 세 번 요청되어도 집합에는 하나만 남는다. 이 줄에는 Play 호출이 없으므로 즉시 소리가 나지는 않는다.

Queue라는 이름을 쓰지만 자료구조는 Queue가 아니라 HashSet이다. 순서대로 모든 소리를 쌓아 반드시 전부 재생하는 방식이 아니라 중복 요청을 합치는 방식이다.

### 22-20. FlushSounds 첫 조건: 너무 가까운 재생 요청 건너뛰기

```csharp
if (lastPlayed.TryGetValue(name, out double previous)
    && time - previous < 0.06) continue;
```

TryGetValue는 해당 키가 있으면 true를 반환하면서 값을 previous에 넣는다. 없으면 false를 반환한다. out은 함수가 호출자에게 값을 전달할 때 사용하는 매개변수 지정이다.

&&이므로 기록을 찾지 못하면 뒤의 시간 비교는 실행하지 않는다. 찾았고 마지막 기록과의 차이가 0.06초 미만이면 이번 항목을 건너뛴다.

예: 마지막 10.00초, 이번 10.03초면 건너뛰고, 10.08초면 재생할 수 있다. 이 값은 효과음 길이가 아니라 **같은 소리를 다시 시작시키는 최소 간격**이다.

### 22-21. FlushSounds 재생·기록·목록 비우기

```csharp
if (sounds.TryGetValue(name, out G2Audio? sound)) sound.Play();
lastPlayed[name] = time;
```

소리 객체가 등록되어 있으면 Play한다. Dictionary의 대괄호 대입은 키가 없으면 추가하고 있으면 값을 바꾼다. 앞서 생성자의 Add와 차이가 있다.

현재 코드에서는 소리를 찾지 못해도 lastPlayed에 시간이 기록된다. 따라서 이 표는 모든 상황에서 “실제로 들린 시각”을 완벽하게 증명하는 데이터는 아니다. 정상적으로 등록된 효과음 이름을 사용하는 흐름에서 재생 간격을 관리한다.

foreach가 끝나면 pendingSounds.Clear로 요청 목록을 비운다. 최소 간격 때문에 건너뛴 요청도 이후에 다시 재생하려고 보관하지 않고 버린다. 이 동작이 타격음이 겹쳐 지나치게 반복되는 것을 줄인다.

### 22-22. UpdateMusic: 매 프레임 새로 시작하지 않게 하기

```csharp
if (music == null) return;
if (enabled && !music.IsPlaying()) music.Play(true);
else if (!enabled && music.IsPlaying()) music.Stop();
```

BGM 객체가 없으면 종료한다. 켜야 하고 아직 재생 중이 아닐 때만 Play(true)한다. true는 반복 재생 옵션이다. 이미 재생 중이면 건드리지 않으므로 매 프레임 음악의 처음으로 돌아가지 않는다.

꺼야 하고 재생 중이면 Stop한다. 이 구조는 일시정지 위치를 저장했다가 이어 듣는 pause/resume 방식은 아니다. 중단 후 다시 재생하면 현재 오디오 구현에서는 처음부터 시작한다.

enabled는 호출자가 정한 값이다. GameMain은 사용자 음악 설정과 일시정지 여부를 함께 고려해 전달한다.

### 22-23. StopSounds: 효과음과 재생 요청 정리

pendingSounds를 비우고 lastPlayed 기록을 비운 뒤 sounds.Values를 순회하며 모든 효과음을 Stop한다. Values는 Dictionary에 저장된 값 객체들의 모음이다. 키 문자열이 필요한 것이 아니므로 값만 순회한다.

**중요:** 이 함수는 music.Stop을 호출하지 않는다. 이름과 달리 BGM까지 전부 멈추는 것은 아니다. 창 비활성 처리에서는 GameMain이 StopSounds 다음에 UpdateMusic(false)를 별도로 호출해서 음악도 멈춘다.

Stop은 재생을 멈추는 것이지 자원을 완전히 해제하는 Dispose와는 다르다. 나중에 같은 효과음 객체를 다시 재생할 수 있다.

### 22-24. Dispose: 리소스 수명 끝내기

코드 순서는 다음과 같다.

1. music이 있으면 Dispose하고 null로 바꾼다.
2. sounds.Values의 각 효과음을 Dispose한다.
3. sounds Dictionary를 비운다.
4. images.Values의 각 텍스처를 Dispose한다.
5. images Dictionary와 pendingSounds를 비운다.

Clear만 호출한다고 Dictionary가 각 값 객체의 Dispose까지 자동으로 호출하는 것은 아니다. 그래서 foreach로 해제한 뒤 Clear한다.

lastPlayed는 현재 Dispose에서 별도로 Clear하지 않는다. 문자열과 숫자를 보관하는 관리 객체이며 그래픽·오디오 자원을 가진 표가 아니다. GameAssets 자체가 더 이상 참조되지 않으면 관리 메모리는 가비지 컬렉션 대상이 된다.

Dispose는 사용을 끝낼 때 호출한다. 호출 후에도 images에서 그림을 찾아 계속 그릴 수 있다고 가정하면 안 된다. GameMain이 GameAssets를 정리하고 자신의 참조도 null로 바꾼다.

## 23. GameRules.cs 처음부터 끝까지 — 여러 파일이 함께 쓰는 규칙

이 장은 `src/ActionGame/GameRules.cs`의 실제 선언 순서를 따른다. GameRules는 현재 체력이나 위치처럼 매 프레임 변하는 상태를 저장하는 클래스가 아니다. **공통 설정값과 간단한 계산 규칙을 모아 둔 클래스**다.

### 23-01. namespace와 주석: 숫자를 한곳에 모으는 이유

```csharp
namespace ActionGame
{
    // 여러 파일에서 같은 숫자를 쓰므로 한곳에 모은다.
    // const는 실행 중 바뀌지 않는 값이다. static 클래스는 new 없이 사용한다.
```

ActionGame은 게임 코드의 이름 공간이다. 주석은 이 파일의 목적을 설명한다. 예를 들어 공격 간격 0.4를 전투 코드와 HUD에 따로 쓰면 한쪽만 고쳐 서로 다르게 동작할 수 있다. 두 곳이 GameRules.KickCooldown을 읽으면 같은 설정을 공유한다.

다만 모든 숫자가 이 파일로 모인 것은 아니다. 현재 코드의 기본 라운드 보너스 300, 적 체력 2, 일부 화면의 총 구역 수 3 등은 다른 곳에도 직접 적혀 있다. 공통 상수를 바꿀 때는 관련 사용처까지 확인해야 한다.

### 23-02. internal static class GameRules

```csharp
internal static class GameRules
```

internal은 같은 어셈블리 안에서 접근할 수 있다는 뜻이다. static 클래스는 `new GameRules()`로 객체를 만들지 않고 클래스 이름으로 멤버를 사용한다.

```csharp
int hp = GameRules.MaxHp;
int count = GameRules.EnemyCount(2);
```

이 클래스는 플레이어마다 별도 규칙 객체가 필요한 것이 아니라 모두 같은 규칙을 사용하므로 static으로 구성했다. static 클래스 안에는 인스턴스 상태나 인스턴스 메서드를 둘 수 없다. const는 형식에 속하는 상수라서 `static const`처럼 static을 추가로 쓰지 않는다.

### 23-03. MaxHp와 RoundCount: 체력 한도와 라운드 수

```csharp
public const int MaxHp = 5;
public const int RoundCount = 3;
```

public은 다른 코드에서 읽을 수 있게 하고, const는 컴파일할 때 값이 정해지는 상수라는 뜻이다. 초기화 뒤 `GameRules.MaxHp = 10`처럼 대입하면 컴파일되지 않는다.

MaxHp는 Player 초기 체력, 정비 회복 상한, HUD 체력 아이콘 등에 사용한다. `player.Hp`는 실제로 줄고 늘어나는 필드이고 MaxHp는 그 기준값이다.

RoundCount는 마지막 라운드인지 판단할 때 사용한다. 현재 3이다. 이것만 4로 바꾼다고 완전한 4라운드 게임이 되는 것은 아니다. 구역 이름 함수·로비 카드 반복 수·화면 문구·기믹 조건도 함께 맞춰야 한다.

### 23-04. KickCooldown: 공격 간격의 기준값

```csharp
public const float KickCooldown = 0.4f;
```

0.4초를 뜻한다. f는 소수 리터럴을 float로 지정한다. 게임에서 사용하는 시간과 좌표가 float이므로 맞춘 것이다.

GameMain.Kick이 공격할 때 `player.KickCooldown = GameRules.KickCooldown`으로 남은 시간을 채운다. 이후 Update가 플레이어의 남은 시간만 줄인다. GameRules의 상수 0.4는 줄어들지 않는다.

HUD는 같은 상수를 분모로 사용해 공격 준비 비율을 구한다. 따라서 값을 바꾸면 공격 간격과 표시가 함께 바뀐다. 현재 계산에서는 이 값을 양수로 두어야 한다. 0을 넣어도 모든 관련 계산이 안전하게 처리되는 구조는 아니다.

### 23-05. LaunchSpeed와 FlyDuration: 날아가기 시작 설정

```csharp
public const float LaunchSpeed = 600;
public const float FlyDuration = 0.65f;
```

LaunchSpeed는 날려 보낼 때의 초기 속도 크기다. FlyDuration은 날아갈 수 있는 남은 시간의 초기값이다.

방향 (1,0)에 속도 600을 곱하면 Velocity=(600,0)이 된다. 방향 (0.6,0.8)이면 (360,480)이다. GameMain.LaunchEnemy가 이 값을 실제 Enemy 필드에 넣는다.

600×0.65=390이지만 실제로 꼭 390만큼 날아가는 것은 아니다. 이동하면서 속도가 감속하고, 벽 충돌이나 사망이 먼저 발생할 수도 있기 때문이다. 설정과 실제 결과를 구분하자.

### 23-06. DefeatScore와 ChainScore: 사건별 점수

```csharp
public const int DefeatScore = 100;
public const int ChainScore = 50;
```

DefeatScore는 적이 제거될 때의 처치 점수다. ChainScore는 날아가는 적이 다른 적에게 충돌했을 때의 연쇄 점수다. 소수 점수를 사용하지 않으므로 int다.

연쇄 충돌로 적이 죽었다면 해당 충돌의 50점과 제거 단계의 100점이 모두 발생할 수 있다. 두 상수는 서로 다른 사건의 보상이다. 라운드 완료 보너스는 별도로 계산한다.

AddScore는 실제 점수를 더하면서 같은 points로 점수 팝업도 만들기 때문에 DefeatScore를 바꾸면 처치 점수와 그 글자에 반영된다.

### 23-07. HazardCycle, HazardWarning, HazardStart: 전기 시간표

```csharp
public const float HazardCycle = 6;
public const float HazardWarning = 2.5f;
public const float HazardStart = 4;
```

HazardCycle은 한 주기의 길이, HazardWarning은 주기 안에서 경고가 시작되는 시점, HazardStart는 실제 전류가 시작되는 시점이다. 세 값 모두 “각 구간의 길이”인 것은 아니다.

| 주기 안의 시간 | 상태 | 구간 길이 |
| --- | --- | --- |
| 0 이상 2.5 미만 | 대기·충전 | 2.5초 |
| 2.5 이상 4 미만 | 경고 | 1.5초 |
| 4 이상 6 미만 | 작동 | 2초 |

GameMain은 `roundTime % HazardCycle`로 현재 주기 위치를 계산한다. 전투 10.2초이면 약 4.2이므로 작동 구간이다. 주기 길이 6을 넘으면 나머지가 다시 0부터 시작한다.

수정할 때는 보통 `0 < HazardWarning < HazardStart < HazardCycle` 관계를 유지한다. 특히 Cycle을 0으로 바꾸면 정상적인 주기 계산이 되지 않는다. 또한 현재 DrawElectricArcs에는 경고 시작 2.5가 직접 적힌 부분이 있으므로 상수 변경 시 그 출력 코드도 확인해야 한다.

### 23-08. ReadyDuration: 전투 전 준비 시간

```csharp
public const float ReadyDuration = 1.5f;
```

각 라운드 시작 때 준비 시간을 1.5초로 설정한다. GameMain.StartRound가 readyTime에 복사하고 Update가 줄인다. 준비 중에는 적 이동·공격·보너스용 roundTime 증가를 건너뛴다.

GameHud.DrawReady는 이 값을 분모로 사용해 준비 막대를 채운다. ReadyDuration은 설정값, readyTime은 현재 남은 값이다.

### 23-09. EnemyCount 함수의 선언

```csharp
public static int EnemyCount(int round)
```

public은 다른 코드에서 사용 가능, static은 객체 없이 호출, int는 돌려줄 값의 형식, EnemyCount는 함수 이름이다. 괄호의 `int round`는 호출자가 전달한 라운드 번호를 받는다.

여기의 round는 매개변수다. GameMain의 round 필드와 이름이 같아도 다른 변수다. `EnemyCount(round)`로 호출하면 호출자가 읽은 정수 값을 이 함수의 매개변수로 전달한다.

### 23-10. return 4 + round * 2: 적 수 계산

```csharp
return 4 + round * 2;
```

곱셈을 덧셈보다 먼저 한다.

| 전달한 round | 계산 | 반환값 |
| --- | --- | --- |
| 1 | 4+1×2 | 6 |
| 2 | 4+2×2 | 8 |
| 3 | 4+3×2 | 10 |

return은 계산값을 호출한 곳에 돌려주고 함수를 끝낸다. `int count = GameRules.EnemyCount(2);`이면 count에 8이 들어간다.

이 함수는 적 객체를 생성하지 않는다. 몇 대인지 숫자만 알려 준다. 실제 생성은 GameMain.StartRound가 한다. 입력 범위 검사는 없으므로 0을 넣으면 4, 4를 넣으면 12가 나온다. 현재 게임이 1~3을 전달한다는 흐름에 맞춘 함수다.

### 23-11. RoundName: 조건에 맞는 이름 반환

```csharp
public static string RoundName(int round)
{
    if (round == 1) return "고철 정리";
    if (round == 2) return "전력 누출";
    return "과부하";
}
```

반환 형식 string이므로 문자열을 돌려준다. `==`는 같은지 비교하는 연산자이고 `=` 대입과 다르다.

round가 1이면 첫 return에서 종료한다. 2라면 첫 조건을 통과하지 않고 두 번째 return에서 종료한다. 둘 다 아니면 마지막 문자열을 돌려준다. 각 return이 함수를 끝내기 때문에 여기서 반드시 else if를 사용할 필요는 없다.

**주의:** 마지막 줄은 `round == 3`을 직접 검사하지 않는다. 따라서 0이나 99를 넣어도 “과부하”다. 현재 호출 흐름에서 정상 구역 번호를 준다는 전제이며, 함수 자체가 입력 오류를 검증하는 것은 아니다.

### 23-12. TimeBonus: 경과 시간을 점수로 바꾸기

```csharp
public static int TimeBonus(float elapsed)
{
    return Math.Max(0, 600 - (int)elapsed * 10);
}
```

elapsed는 지난 시간이다. 입력은 소수인 float, 출력은 정수 점수 int다.

계산 순서를 분리하면 다음과 같다.

1. `(int)elapsed`로 소수 부분을 버린다. 현재 경과 시간은 0 이상이다.
2. 정수 초에 10을 곱해 시간에 따른 차감을 구한다.
3. 최대 시간 점수 600에서 차감을 뺀다.
4. 결과와 0 중 큰 값을 골라 음수 보너스를 막는다.

| elapsed | 정수 초 | 600-초×10 | 최종 반환값 |
| --- | --- | --- | --- |
| 0 | 0 | 600 | 600 |
| 12.9 | 12 | 480 | 480 |
| 30 | 30 | 300 | 300 |
| 60 | 60 | 0 | 0 |
| 75 | 75 | -150 | 0 |

`(int)elapsed * 10`과 `(int)(elapsed * 10)`은 다르다. 12.9에서는 앞 식은 120, 뒤 식은 대략 129이므로 괄호 위치에 따라 결과가 바뀐다.

이 함수는 시간 보너스만 반환한다. 기본 300과 체력×50을 더하는 것은 GameMain.CheckRoundEnd다. 함수 자체는 score를 변경하지 않는다. 음수 elapsed에 대한 별도 검사는 없으므로, 예를 들어 -2를 주면 620을 반환한다. 정상 전투 시간이라는 입력 전제를 기억하자.

### 23-13. GameRules와 상태 필드 구분

| 고정 규칙 | 변하는 상태 | 연결 |
| --- | --- | --- |
| MaxHp=5 | player.Hp | 초기값·회복 상한에 사용 |
| KickCooldown=0.4 | player.KickCooldown | 공격할 때 설정값을 복사하고 상태만 감소 |
| FlyDuration=0.65 | enemy.FlyTime | 날아가기 시작 시 복사하고 상태만 감소 |

규칙이 같아도 각 객체의 현재 상태는 다를 수 있다. 두 적이 같은 FlyDuration을 사용해도 공격받은 시점이 다르면 FlyTime은 다르다.

## 24. GameEffect.cs 처음부터 끝까지 — 잠깐 재생되는 이미지 효과

이 장은 `src/ActionGame/GameEffect.cs`의 실제 순서를 따른다. GameEffect는 타격·파괴 같은 이미지 효과 하나의 정보를 저장한다. 파일을 로딩하거나 직접 그림을 그리지는 않는다. GameMain이 시간을 갱신하고, GameAssets가 지정된 프레임을 그린다.

### 24-01. namespace와 첫 주석

```csharp
namespace ActionGame
{
    // 적이 제거되어도 남은 파괴 애니메이션을 끝까지 재생한다.
```

효과가 적과 별도 객체인 이유를 설명하는 주석이다. 적을 enemies에서 제거해도 효과는 effects 목록에 따로 있으므로 바로 사라지지 않는다. 효과 객체에 필요한 좌표와 시트 이름을 복사해 놓았기 때문이다.

### 24-02. internal sealed class GameEffect

internal은 같은 어셈블리 내부에서 사용한다는 뜻이다. sealed는 다른 클래스의 상속을 막는다. GameEffect는 IDisposable을 구현하지 않는다.

여기에는 G2Texture나 오디오 장치를 직접 가진 필드가 없다. 실제 그래픽 자원은 GameAssets가 소유하고, GameEffect는 이름·좌표·숫자 상태만 보관한다. 따라서 이 클래스에는 자체 그래픽 해제 함수가 없다.

### 24-03. Sheet: 어떤 시트를 쓸 것인가

```csharp
public string Sheet { get; }
```

필드처럼 이름만 선언한 것이 아니라 **자동 구현 속성**이다. get은 값을 읽는 접근자다. set이 없어서 외부에서 `effect.Sheet = ...`처럼 바꿀 수 없다. 이 형태의 읽기 전용 자동 속성은 생성자에서 초기값을 대입할 수 있다.

Sheet에는 `"hit_spark_sheet"` 같은 이미지 키가 들어간다. 이미지 파일의 전체 경로나 이미지 픽셀 데이터 자체를 저장하는 것이 아니다. GameAssets의 images Dictionary에 등록된 키와 맞아야 한다.

### 24-04. X와 Y: 효과가 생긴 위치

```csharp
public float X { get; }
public float Y { get; }
```

이 효과를 그릴 게임 좌표다. 생성자에서 정하고 외부에서 바꾸지 않는다. Update도 X/Y를 변경하지 않으므로 현재 GameEffect는 생성된 위치에 머무르는 효과다.

적의 좌표를 전달할 때 float 값이 복사된다. 이후 적이 움직이거나 제거되어도 이미 만들어진 효과의 X/Y가 자동으로 따라 바뀌지 않는다. “적 객체를 계속 추적하는 효과”와는 다른 구현이다.

### 24-05. Size와 Angle: 출력 크기와 회전

```csharp
public float Size { get; }
public float Angle { get; }
```

Size는 화면에 표시할 크기다. 예를 들어 88을 전달하면 GameAssets.DrawFrame이 88×88의 출력 영역을 사용한다. 원본 시트의 한 칸 크기 128과는 다르다.

Angle은 라디안 단위의 회전 각도다. 0은 기본 방향, π/2는 90도에 해당한다. 벽 충돌 효과를 어느 벽에 맞았는지에 따라 돌려 그릴 때 사용한다. 둘 다 생성 시 정하고 이후 유지한다.

### 24-06. Duration: 효과를 보여 줄 전체 시간

```csharp
public float Duration { get; }
```

Duration은 총 재생 시간이다. duration=0.4라면 약 0.4초 동안 네 프레임을 보여 주려는 설정이다. 남은 시간이 아니라 **전체 길이**이므로 Update에서 줄이지 않는다.

현재 생성자에는 duration을 검사하는 코드가 없다. 프레임 계산에서 나눗셈의 분모로 사용하므로 호출자가 양수 값을 주어야 한다. 실제 게임 호출은 0.2, 0.28, 0.4 등 양수 시간을 사용한다.

### 24-07. Age: 지금까지 지난 시간

```csharp
public float Age { get; private set; }
```

Age는 이 효과가 시작한 뒤 흐른 시간이다. get은 public이므로 밖에서 읽을 수 있지만 set은 private여서 GameEffect 내부에서만 값을 대입할 수 있다. 처음 값은 float의 기본값 0이다.

| 코드 | 가능 여부 |
| --- | --- |
| 외부에서 `float t = effect.Age;` | 가능 |
| 외부에서 `effect.Age = 1;` | 불가능 |
| GameEffect.Update 안에서 `Age += dt;` | 가능 |

Duration이 전체 재생 시간, Age가 경과 시간이다. 남은 시간은 필요하다면 Duration-Age로 생각할 수 있지만 현재 코드에는 별도 남은 시간 필드를 두지 않았다.

### 24-08. Frame: 경과 시간으로 그림 번호 계산

```csharp
public int Frame => Math.Clamp((int)(Age / Duration * 4), 0, 3);
```

Frame은 계산 속성이다. 별도 필드에 번호를 계속 저장하는 것이 아니라 읽는 순간 Age와 Duration으로 계산한다.

1. Age/Duration: 전체 시간 중 얼마나 지났는지 비율을 구한다.
2. 비율×4: 네 프레임 구간 중 어디인지 계산한다.
3. (int): 소수 부분을 버려 정수 번호로 만든다.
4. Clamp: 0~3 사이로 제한한다.

Duration=0.4인 경우의 대표 계산은 다음과 같다. 아래는 수식을 이해하기 위한 값이며 실제 float에는 작은 오차가 있을 수 있다.

| Age | 진행 비율 | ×4 후 정수 변환 | Frame |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 0.05 | 0.125 | 0 | 0 |
| 0.15 | 0.375 | 1 | 1 |
| 0.25 | 0.625 | 2 | 2 |
| 0.35 | 0.875 | 3 | 3 |
| 0.45 | 1.125 | 4 | 3 |

0.45에서 4번 이미지를 읽지 않도록 마지막 프레임 3으로 제한한다. 이것은 `%4`로 처음 프레임부터 반복하는 동작이 아니다. GameEffect는 현재 한 번 재생되는 효과다.

프레임당 시간은 Duration/4다. 총 0.4초라면 한 칸에 약 0.1초다. 프레임 갱신 간격 dt가 크면 중간 번호를 건너뛸 수도 있으며, 모든 프레임을 반드시 같은 횟수로 화면에 그리는 구조는 아니다.

### 24-09. Finished: 끝났는지 알려 주는 속성

```csharp
public bool Finished => Age >= Duration;
```

경과 시간이 전체 시간 이상이면 true다. 읽을 때 현재 값을 비교한다. >=이므로 같아진 순간에도 끝났다고 판단한다.

Finished가 true라고 객체가 자동으로 목록에서 사라지는 것은 아니다. GameMain.UpdateEffects가 이 속성을 검사하고 `effects.RemoveAt(i)`를 호출한다.

현재 처리 순서는 효과 Update → Finished 검사 → 끝났으면 제거 → 나중에 Render다. 따라서 Age가 이미 Duration 이상이면 Frame 속성 자체는 3을 반환할 수 있어도, 정상 목록 처리에서는 제거되어 다음 Render에서 그리지 않는다.

### 24-10. 생성자: 효과 하나의 초기 정보를 받기

```csharp
public GameEffect(string sheet, float x, float y,
    float size, float duration, float angle = 0)
```

생성자는 클래스 이름과 같고 반환 형식을 쓰지 않는다. 시트 이름·위치·크기·시간·각도를 전달받는다. angle=0은 생략 가능한 기본 매개변수다.

```csharp
new GameEffect("enemy_break_sheet", 200, 300, 88, 0.4f)
```

이 호출은 위치 (200,300), 크기 88, 전체 시간 0.4, 각도 0인 효과를 만든다. angle을 따로 넘기면 그 값으로 생성한다. 매개변수 없는 생성자는 선언하지 않았으므로 `new GameEffect()`는 사용할 수 없다.

### 24-11. 생성자 본문: 매개변수를 속성에 저장

```csharp
Sheet = sheet; X = x; Y = y;
Size = size; Duration = duration; Angle = angle;
```

원본은 여러 대입문을 한 줄에 썼지만 `;`마다 별개의 문장이다. 대문자로 시작한 이름은 속성, 소문자 이름은 이번 생성자 호출의 매개변수다. C#은 대소문자를 구분한다.

오른쪽 값을 읽어 왼쪽 속성에 저장한다. get만 있는 자동 속성이지만 이 클래스의 생성자에서는 대입할 수 있다. Age는 여기서 대입하지 않으므로 기본값 0으로 시작한다.

### 24-12. Update: 시간만 앞으로 보내기

```csharp
public void Update(float dt)
{
    Age += dt;
}
```

void는 반환값이 없다는 뜻이다. `Age += dt`는 `Age = Age + dt`와 같다. 한 번 호출할 때 지난 시간을 더한다.

Age가 0.12이고 dt=0.03이면 새 Age는 약 0.15다. 이 함수는 그림을 그리거나 스스로를 제거하지 않는다. 시간 상태를 갱신하면 Frame과 Finished를 나중에 읽을 때 결과가 달라진다.

호출하지 않으면 시간이 실제로 흘러도 Age는 저절로 증가하지 않는다. 일시정지 때 GameMain이 UpdateEffects를 건너뛰므로 효과도 멈춘다. 시간 측정용 별도 스레드나 타이머가 이 클래스 안에 있는 것이 아니다.

### 24-13. 생성부터 제거까지 연결하기

```text
GameMain.AddEffect
→ new GameEffect(이름, 위치, 크기, 시간, 각도)
→ effects 목록에 추가
매 프레임 GameMain.UpdateEffects
→ effect.Update(dt)로 Age 증가
→ Finished이면 목록에서 제거
GameMain.Render
→ 남아 있는 effect의 Sheet, Frame, X, Y 등을 읽음
→ GameAssets.DrawFrame으로 해당 그림 한 칸 출력
```

예를 들어 적이 파괴될 때 효과를 먼저 등록하고 적을 제거한다. 효과는 필요한 위치를 이미 저장했으므로 적 객체가 목록에서 없어져도 자기 Duration 동안 재생할 수 있다.

GameMain.AddEffect에는 효과가 64개 이상이면 오래된 것을 제거하는 제한도 있다. 따라서 “모든 효과가 어떤 상황에서도 반드시 전체 시간을 재생한다”는 보장은 아니다. 일반적인 상황에서는 수명대로 끝나고, 과도하게 쌓일 때는 수 제한이 먼저 작동할 수 있다.

### 24-14. GameEffect 복습 문제

| 질문 | 답 |
| --- | --- |
| Sheet에는 PNG 픽셀 데이터가 들어 있는가? | 아니다. GameAssets에서 찾을 문자열 키다. |
| 외부에서 effect.X를 바꿀 수 있는가? | 현재 get 전용 속성이므로 직접 대입할 수 없다. |
| 외부에서 Age를 읽고 쓸 수 있는가? | 읽기는 가능, 직접 대입은 private set 때문에 불가능. |
| Duration=0.4, Age=0.25일 때 Frame은? | 2. |
| Duration=0.4, Age=0.45일 때 Frame과 Finished는? | Frame=3, Finished=true. |
| Finished가 true면 객체가 자동으로 삭제되는가? | 아니다. GameMain이 목록에서 제거한다. |
| 효과가 생성된 뒤 적이 움직이면 효과도 따라가는가? | 아니다. 위치 값을 복사했고 Update는 좌표를 바꾸지 않는다. |
| Update를 호출하지 않아도 Age가 자동 증가하는가? | 아니다. dt를 더하는 호출이 필요하다. |
| 프레임 계산에서 Clamp 대신 %4를 쓰면 같은가? | 아니다. Clamp는 범위 끝에 제한하고 %는 반복 번호를 만든다. |
| 이 클래스에 Dispose가 없는 이유는? | 실제 이미지 장치 자원을 소유하지 않고 이름과 수치만 보관하기 때문이다. |

## 25. ScorePopup.cs 처음부터 끝까지 — 올라갔다 사라지는 점수 글자

이 장은 `src/ActionGame/ScorePopup.cs`의 실제 순서를 따른다. 팝업은 화면에 잠시 나타나는 표시다. ScorePopup은 “처치 +100” 같은 글자의 내용·위치·남은 시간만 관리한다. **실제 누적 점수를 보관하거나 더하는 클래스가 아니다.**

### 25-01. namespace와 역할 주석

```csharp
namespace ActionGame
{
    // 점수는 GameMain에서 실제로 더한다. 이 클래스는 화면에 떠오르는 글자만 관리한다.
```

이 주석은 게임 데이터와 시각 표현을 분리했다는 뜻이다. 점수는 오래 유지되어야 하지만 팝업은 0.8초 뒤 사라져야 하므로 같은 변수로 관리하지 않는다.

팝업을 지우거나 숨겨도 이미 얻은 점수가 사라지지 않는 이유다.

### 25-02. internal class ScorePopup

internal은 같은 어셈블리 안에서 사용하는 클래스라는 뜻이다. GameEffect와 달리 sealed가 붙어 있지는 않지만 현재 게임에서 ScorePopup을 상속하는 클래스는 없다.

별도의 그래픽 자원을 생성하지 않으며 IDisposable도 구현하지 않는다. 글꼴과 실제 그리기는 GameHud에 맡긴다.

### 25-03. X와 Y: 글자를 띄울 기준 위치

```csharp
public float X;
public float Y;
```

두 필드는 생성자에서 전달받은 좌표를 저장한다. float이므로 소수 이동도 가능하다. GameEffect의 get 전용 속성과 달리 일반 public 필드이므로 외부에서도 직접 바꿀 수 있다.

현재 Update는 Y만 바꾸고 X는 그대로 둔다. 따라서 글자가 좌우로 흔들리지 않고 위로 올라간다. GameHud.DrawScorePopup은 이 좌표에서 글자 박스의 시작 위치를 보정해 적 위에 표시한다. X/Y가 항상 글자 박스 왼쪽 위 자체인 것은 아니다.

### 25-04. Text: 화면에 출력할 완성된 문자열

```csharp
public string Text;
```

Text는 글자 내용이다. 선언 줄에 초기값이 없지만 생성자에서 반드시 문자열을 대입한다. 숫자 points를 별도 필드로 저장하는 구조가 아니다. 생성할 때 “처치 +100”처럼 출력할 문자열을 만들어 둔다.

이 Text는 G2Font나 GameHud.Text 함수와 다른 것이다. 이름이 같거나 비슷해도 소속을 함께 읽어야 한다. `popup.Text`는 문자열 필드이고, GameHud의 Text(...)는 글자를 그리는 함수다.

### 25-05. Life = 0.8f: 남은 표시 시간

```csharp
public float Life = 0.8f;
```

Life는 남아 있는 표시 시간이며 처음 0.8초다. GameEffect.Age와 방향이 반대다. Age는 0부터 증가하고 Life는 0.8부터 감소한다.

Life는 const가 아니다. Update가 계속 줄인다. static도 아니므로 각 팝업마다 별도 값이다. 나중에 생긴 팝업은 앞서 생긴 팝업이 곧 사라지더라도 자신의 0.8초를 가지고 시작한다.

### 25-06. 생성자: 위치·점수·이유 받기

```csharp
public ScorePopup(float x, float y, int points, string reason)
```

x/y는 팝업 위치, points는 표시할 점수, reason은 “처치”나 “연쇄” 같은 이유다. 모든 인수를 전달해야 한다. 이 생성자에는 기본값으로 생략 가능한 인수가 없다.

```csharp
new ScorePopup(200, 300, 100, "처치")
```

이 호출은 위치 (200,300)에 보여 줄 “처치 +100” 팝업 객체를 만든다. 단지 객체를 만드는 것만으로 실제 score가 100 증가하지는 않는다.

### 25-07. 생성자 본문: 값 대입과 문자열 연결

```csharp
X = x;
Y = y;
Text = reason + " +" + points;
```

X/Y는 필드, x/y는 생성자 매개변수다. float 숫자를 복사해 저장한다.

마지막 줄의 `+`는 숫자 덧셈이 아니라 문자열 연결에 사용된다. reason과 `" +"`를 연결하고 points를 문자열 표현으로 이어 붙인다.

| reason | points | 완성된 Text |
| --- | --- | --- |
| 처치 | 100 | 처치 +100 |
| 연쇄 | 50 | 연쇄 +50 |
| 보너스 | 300 | 보너스 +300 |

`" +"`에는 공백 한 칸과 더하기 기호가 들어 있다. 이 더하기 기호는 계산 연산이 아니라 출력 문자다.

현재 생성자는 points가 음수인지 검사하지 않는다. -100을 넣으면 “처치 +-100”처럼 될 수 있다. 실제 게임이 양수 보상 값을 전달한다는 사용 흐름에 맞춘 표현이다. N0 같은 숫자 포맷은 여기서 사용하지 않는다.

### 25-08. Update의 첫 줄: 글자를 위로 이동

```csharp
Y -= 30 * dt;
```

`-=`는 현재 값에서 오른쪽 값을 뺀 뒤 저장한다. 화면에서는 Y가 아래로 증가하므로 빼면 위로 올라간다. 30은 게임 좌표 기준 초당 이동량이다.

Y=300, dt=0.1이라면 30×0.1=3을 빼서 Y=297이 된다. dt=0.05면 1.5만큼 올라간다. 프레임마다 무조건 30씩 빼면 컴퓨터가 더 자주 갱신할수록 너무 빨리 올라가므로 dt를 곱한다.

X는 수정하지 않으므로 가로 위치는 그대로다. 실제 화면에서 보이는 픽셀 이동량은 전체 화면 출력 배율에 따라 커질 수 있지만 게임 좌표 속도는 동일하다.

### 25-09. Update의 두 번째 줄: 남은 시간 감소

```csharp
Life -= dt;
```

Life에서 이번 프레임의 시간만큼 뺀다. 처음 0.8에서 dt=0.1이면 약 0.7이다. GameMain.UpdateEffects는 이 호출 뒤 Life<=0을 확인해 팝업을 목록에서 제거한다.

이 클래스 자체는 Life를 0으로 Clamp하지 않는다. 0.02에서 0.05를 빼면 약 -0.03이 될 수 있다. 하지만 외부 코드가 <=0으로 제거하기 때문에 정상 흐름에서 끝난 팝업을 계속 보여 주지 않는다.

또 Update에서 “이미 끝났으면 return”하는 조건도 없다. 종료 여부 판단과 제거를 호출자인 GameMain이 맡는 구조다.

### 25-10. 위치와 수명을 함께 계산해 보기

생성 직후 X=200, Y=300, Life=0.8이라고 하자. 누적 갱신 시간을 기준으로 계산하면 다음과 같다. float 오차와 프레임 경계에 따라 실제 제거 시점은 한 갱신 단위 차이가 날 수 있다.

| 누적 갱신 시간 | X | Y 계산 | Life 계산 |
| --- | --- | --- | --- |
| 0 | 200 | 300 | 0.8 |
| 0.2 | 200 | 300-30×0.2=294 | 0.6 |
| 0.4 | 200 | 288 | 0.4 |
| 0.6 | 200 | 282 | 0.2 |
| 0.8 | 200 | 276 | 0 |

수명 0.8초 동안 위로 이동하는 거리는 이론상 30×0.8=24다. 끝나면서 Life<=0이면 그 프레임의 검사에서 제거되므로 마지막 위치가 반드시 화면에 한 번 더 그려진다는 뜻은 아니다.

현재 게임은 준비·결과 등에서도 일시정지가 아니면 화면 효과를 갱신한다. 일시정지나 창 비활성으로 UpdateEffects가 호출되지 않는 동안은 팝업도 멈춘다.

### 25-11. 실제 점수와 팝업이 함께 생기는 위치

GameMain.AddScore를 연결해서 읽어 보자.

```csharp
score += points;
if (scorePopups.Count >= 24) scorePopups.RemoveAt(0);
scorePopups.Add(new ScorePopup(x, y, points, reason));
```

첫 줄이 실제 점수 증가다. 마지막 줄이 시각 표시 등록이다. 둘은 같은 points를 사용하지만 다른 역할이다.

기존 score=200, points=100이면 실제 점수는 300이 되고, 팝업 문자열은 “처치 +100”이 된다. 팝업은 누적 점수 300을 보여 주는 것이 아니라 이번에 얻은 100을 보여 준다.

목록이 이미 24개라면 오래된 팝업을 하나 제거해 수를 제한한다. 수명 전에 제거될 수 있어도 첫 줄에서 더한 실제 점수는 유지된다.

### 25-12. 화면에 그리기와 투명도는 GameHud가 담당

GameMain.Render가 각 팝업을 GameHud.DrawScorePopup으로 전달한다. GameHud는 다음 계산으로 투명도를 정한다.

```csharp
float opacity = Math.Clamp(popup.Life / 0.4f, 0, 1);
```

Life=0.8이면 2를 1로 제한, 0.6이면 1.5를 1로 제한한다. Life=0.4에서 1, 0.2에서 0.5가 된다. 따라서 첫 절반은 선명하게, 마지막 0.4초는 점점 흐리게 보인다.

ScorePopup 안에는 opacity 필드가 없다. 다른 클래스가 Life를 읽어 화면 표현에 활용하는 예다. Text는 이 시간 동안 그대로지만 Y와 Life가 변하므로 올라가면서 사라져 보인다.

### 25-13. GameEffect와 ScorePopup 비교

| 비교 | GameEffect | ScorePopup |
| --- | --- | --- |
| 표시 내용 | 시트 이미지 한 프레임 | 점수 문자열 |
| 초기 시간 | Age=0, Duration은 생성자로 전달 | Life=0.8 |
| 시간 변화 | Age를 증가 | Life를 감소 |
| 종료 기준 | Age>=Duration | Life<=0 |
| 위치 변화 | Update에서 바꾸지 않음 | Y를 위로 이동 |
| 외부 접근 | 대부분 get 전용 속성 | public 필드 |
| 직접 그림을 그리는가? | 아니며 GameAssets가 그림 | 아니며 GameHud가 글자를 그림 |
| 실제 점수/피해를 계산하는가? | 하지 않음 | 하지 않음 |
| 제거 담당 | GameMain.UpdateEffects | GameMain.UpdateEffects |

둘 다 화면 효과의 정보와 시간을 관리하지만 움직임·종료 표현 방식이 다르다. 어느 쪽이든 목록에서 제거되었다고 이미 일어난 처치·점수 사건을 취소하지 않는다.

### 25-15. 세 파일을 함께 보는 시험 연습

**문제:** 현재 점수 400인 상태에서 적이 제거되었다. 해당 적 위치는 (200,300)이고, 처치 팝업 생성 후 누적 갱신 시간이 0.2초 지났다. 다른 점수 사건은 없다고 할 때 각 값을 설명하라.

**풀이:** GameRules.DefeatScore는 100이다. GameMain.AddScore가 실제 score에 더하므로 점수는 500이다. ScorePopup의 Text는 “처치 +100”이다. X는 200, Y는 300-30×0.2=294, Life는 약 0.6이다. GameHud가 계산하는 투명도는 Clamp(0.6/0.4,0,1)=1이다.

**추가 문제:** 동시에 생성한 Duration=0.4인 파괴 GameEffect의 Age가 0.25라면?

**풀이:** Frame=(int)(0.25/0.4×4)=2, Finished=false다. 위치는 생성 당시 값을 유지한다. 이 효과의 프레임이나 팝업의 위치 변화는 실제 score=500을 바꾸지 않는다.

**직접 수정 연습:** 게임을 바꾸려는 작업이 아니라 이해를 확인하는 연습이다. ScorePopup의 이동 속도 30을 60으로 바꾸면 더 빠르게 올라가지만 Life 초기값이 같으므로 표시 시간은 같다. GameEffect 생성 시 duration을 두 배로 주면 네 프레임이 더 느리게 재생된다. GameRules.DefeatScore를 바꾸면 처치 보상과 팝업에 전달하는 값이 함께 바뀐다. 실습 후에는 원래 값으로 되돌리자.

## 26. Program.cs 처음부터 끝까지 — 게임은 어디서 시작되는가

이 장은 `src/ActionGame/Program.cs`의 실제 코드 순서를 따른다. Program.cs는 짧지만 전체 게임의 출발점이다. **Windows Forms 설정 → 게임 객체 생성 → 게임 반복 실행 → 자원 정리**를 연결한다. 적 이동이나 점수 계산을 직접 작성하는 파일은 아니다.

### 26-01. namespace ActionGame: 프로그램 코드의 소속

```csharp
namespace ActionGame
{
```

ActionGame이라는 이름 공간 안에 Program 클래스를 선언한다. GameMain, Player, Enemy 등과 같은 소속이므로 같은 프로젝트에서 클래스 이름을 사용해 연결할 수 있다.

namespace를 선언했다고 그 안의 클래스들이 위에서 아래로 자동 실행되는 것은 아니다. 프로그램의 진입점인 Main부터 실행 흐름을 따라가야 한다.

### 26-02. internal class Program: 시작 함수를 담는 클래스

```csharp
internal class Program
{
```

internal은 같은 어셈블리 안에서 접근할 수 있다는 뜻이다. Program은 시작 함수 Main을 담는 클래스 이름이다.

Program 클래스 자체에는 static이 붙어 있지 않다. 하지만 아래 Main 메서드는 static이므로 `new Program()` 없이 호출될 수 있다. 이 게임은 Program 객체를 따로 생성하지 않는다.

“클래스에 static이 없으면 그 안에 static 함수도 둘 수 없다”는 생각은 틀리다. 일반 클래스 안에도 static 메서드를 선언할 수 있다.

### 26-03. [STAThread]: 시작 스레드의 실행 방식 표시

```csharp
[STAThread]
```

대괄호로 붙인 것은 **특성(attribute)**이다. 바로 아래 Main 메서드에 대한 추가 정보를 제공한다. 여기서는 프로그램의 시작 스레드가 STA 방식으로 COM과 상호작용하도록 지정한다.

STA는 Single-Threaded Apartment의 약자다. 초보 단계에서는 “Windows UI에서 사용하는 일부 기능과 호환되도록 시작 스레드의 COM 실행 방식을 정하는 표시”로 이해하면 된다. 클립보드, 드래그 앤 드롭, 일부 공용 대화상자 등과 관련된다.

이 특성이 게임 루프를 반복해 주거나, 새 스레드를 만들거나, 프로그램 전체에 스레드를 하나만 허용하는 것은 아니다. 현재 Windows Forms 기반 프로그램의 진입점에 붙은 설정이다.

### 26-04. static void Main(): 프로그램의 진입점

```csharp
static void Main()
```

| 부분 | 뜻 |
| --- | --- |
| static | Program 객체를 만들지 않고 실행 가능한 메서드 |
| void | 호출자에게 값을 돌려주지 않음 |
| Main | 이 프로그램에서 사용하는 진입점 이름 |
| () | 이 선언에서는 전달받는 매개변수가 없음 |

Main에 접근 제한자를 쓰지 않았으므로 클래스 멤버의 기본 접근 수준인 private이다. 프로그램 진입점이라고 반드시 public으로 선언해야 하는 것은 아니다.

이 프로젝트는 명시적으로 작성한 Main을 진입점으로 사용한다. 다른 형태의 C# 프로그램에서는 인수나 정수 반환값을 받는 Main, 최상위 문장 방식도 가능하지만 현재 파일에는 해당하지 않는다.

### 26-05. ApplicationConfiguration.Initialize(): 창 설정 먼저 준비

```csharp
// glc2d도 내부적으로 Windows Forms 창을 사용하므로 먼저 초기화한다.
ApplicationConfiguration.Initialize();
```

Windows Forms 앱의 기본 설정을 초기화한다. 프로젝트 설정에 맞춘 시각 스타일·DPI 등 UI 관련 초기화를 적용하는 시작용 코드다. ApplicationConfiguration은 이 형태의 Windows Forms 프로젝트에서 빌드 도구가 제공하는 초기화 형식이다.

현재 csproj에는 UseWindowsForms=True, ImplicitUsings=enable이 설정되어 있다. 따라서 Program.cs 맨 위에 `using System.Windows.Forms;`가 직접 보이지 않아도 관련 이름을 사용할 수 있다.

이 호출이 “모든 게임 리소스 로딩”까지 하는 것은 아니다. 플레이어 이미지와 효과음은 뒤에서 GameMain.Initialize가 GameAssets를 만들 때 로딩한다.

순서도 중요하다. 이 초기화를 먼저 실행한 뒤 GameMain을 만들어야, 그 생성 과정에서 만드는 Windows 창에 준비된 앱 설정을 적용할 수 있다.

### 26-06. using GameMain game = new GameMain(): 생성과 정리 예약

```csharp
using GameMain game = new GameMain();
```

한 줄이지만 여러 뜻을 가지고 있다.

| 부분 | 뜻 |
| --- | --- |
| using | 현재 범위를 벗어날 때 자원을 정리하도록 하는 using 선언 |
| GameMain | 변수에 저장할 형식 |
| game | 지역 변수 이름 |
| = | 오른쪽 결과를 왼쪽 변수에 대입 |
| new GameMain() | 게임 객체를 새로 생성 |

game은 Main 안에서만 사용하는 지역 변수다. new는 객체를 만들고 생성 과정을 실행한다. GameMain은 G2AppBase를 상속하므로 생성 과정에서 부모의 생성자도 실행되어 창·그래픽·오디오·입력 장치 등을 준비한다.

**중요한 구분:** new GameMain()만으로 GameMain.Initialize가 호출되는 것은 아니다. 이 프로젝트에서는 뒤의 Run이 Initialize를 호출한다. 객체 생성과 게임 실행은 서로 다른 단계다.

### 26-07. 여기의 using은 파일 위쪽 using과 다르다

```csharp
using System.Numerics;                 // 이름 공간을 가져오는 using 지시문
using GameMain game = new GameMain();  // 수명 관리를 위한 using 선언
```

첫 번째는 형식의 긴 이름을 짧게 사용할 수 있게 한다. 두 번째는 객체의 사용이 끝날 때 Dispose가 호출되도록 한다. 단어는 같지만 문맥과 역할이 다르다.

GameMain은 부모 G2AppBase를 통해 IDisposable을 구현하고 Dispose를 override하므로 이 using 선언으로 정리할 수 있다.

using 선언은 이 줄이 끝나자마자 Dispose하는 것이 아니다. **이 선언이 속한 범위, 여기서는 Main의 본문을 벗어날 때** 정리한다. 만약 game.Run() 뒤에 다른 문장이 있었다면 그 문장도 실행한 다음 범위를 벗어나며 정리하게 된다.

### 26-08. using을 try/finally로 풀어 이해하기

핵심 의미를 단순화하면 다음과 비슷하다.

```csharp
GameMain game = new GameMain();
try
{
    game.Run();
}
finally
{
    game.Dispose();
}
```

정상적으로 Run이 끝났거나 객체 생성 이후 사용 중 예외로 범위를 빠져나갈 때도 자원을 정리하기 위한 구조다. 가비지 컬렉터가 언젠가 메모리를 회수할 때까지 그래픽 자원을 계속 들고 있지 않도록 한다.

다만 이 예시는 이해를 위한 코드다. **객체 생성 자체가 실패했다면** 아직 game을 정상적으로 얻은 것이 아니므로 이 using이 완성된 객체를 Dispose해 주는 상황이 아니다. 실제 부모 생성자는 부분적으로 만든 장치를 정리하는 예외 처리를 별도로 가지고 있다.

프로세스 강제 종료나 전원 차단까지 using이 정리를 보장한다는 뜻도 아니다. 정상적인 실행 범위 종료와 예외에 의한 범위 해제에서 자원 관리를 돕는 기능이다.

### 26-09. game.Run(): 반복 실행을 부모에게 맡기기

```csharp
game.Run();
```

점(`.`)은 game 객체의 멤버에 접근한다. 괄호는 함수를 호출한다는 뜻이고, 여기서는 별도 인수를 넘기지 않는다.

Run은 GameMain 파일에 직접 정의된 함수가 아니라 부모 G2AppBase에서 물려받은 함수다. Run 내부에서 게임 초기화와 반복 실행을 연결한다.

```text
Run
→ GameMain.Initialize 한 번
→ 시간 측정 시작
→ 창의 반복 실행
    → 시간·입력 갱신
    → GameMain.Update
    → GameMain.Render
    → 다시 반복
```

이 호출은 게임 창이 돌아가는 동안 바로 다음 줄로 넘어가 끝나는 단순 출력 함수와 다르다. 일반적인 흐름에서는 창을 닫아 반복 실행이 끝나면 Run이 반환하고 Main의 종료로 이어진다.

현재 부모의 Run은 실행 중 예외를 잡아 오류 창을 보여 주는 처리도 포함한다. 오류로 반복 실행이 끝난 경우에도 Run에서 돌아와 using 범위를 벗어나면 생성된 게임 객체의 정리로 이어진다.

### 26-10. 왜 Application.Run 대신 game.Run을 쓰는가

일반적인 Windows Forms 예제에서는 Application.Run(form)을 볼 수 있다. 이 프로젝트는 교수님 glc2d의 G2AppBase가 Vortice의 RenderLoop.Run으로 입력·갱신·그리기를 반복하는 구조다.

따라서 Program에서는 game.Run을 호출한다. GameMain.Update 안에서 다시 Run을 호출하거나 별도의 무한 while문을 추가할 필요가 없다. 반복은 프레임워크가 담당하고 게임은 호출받은 Update와 Render를 구현한다.

### 26-11. 끝의 중괄호와 종료 순서

마지막 중괄호 세 개는 각각 Main 본문, Program 클래스, ActionGame 이름 공간을 닫는다.

일반적인 종료 흐름은 다음과 같다.

```text
사용자가 게임 창을 닫음
→ 반복 실행이 끝남
→ game.Run()에서 돌아옴
→ Main의 범위를 벗어남
→ using 선언이 GameMain.Dispose() 호출
→ HUD·이미지·소리·붓 등 게임 자원 정리
→ base.Dispose()로 부모의 장치 정리
→ Main 종료
```

Program에는 직접 game.Dispose()라는 줄이 없어도 using이 호출을 연결해 준다. Dispose 호출과 “모든 관리 객체의 메모리가 그 순간 즉시 사라짐”은 같은 의미가 아니다. 여기서 중요한 것은 장치 자원을 사용이 끝난 시점에 해제하는 것이다.

### 26-12. Program 전체를 코드 순서대로 말해 보기

1. ActionGame 안에 프로그램 시작용 Program 클래스를 정의한다.
2. Main에 STAThread 특성을 붙여 Windows UI 관련 실행 방식을 지정한다.
3. static Main이 프로그램의 진입점으로 시작된다.
4. ApplicationConfiguration.Initialize로 Windows Forms 설정을 준비한다.
5. new GameMain으로 게임 객체와 부모의 장치·창을 준비한다.
6. using 선언으로 Main 범위 종료 시 자원 정리를 예약한다.
7. game.Run이 Initialize와 Update·Render 반복을 진행한다.
8. Run이 끝나면 범위를 빠져나가며 Dispose하고 Main을 끝낸다.

파일에 적힌 문장은 적지만 다른 파일 전체를 연결하는 역할을 한다. 시험에서는 “Program은 시작점, GameMain은 게임 규칙, G2AppBase는 공통 실행 틀”로 역할을 구분해 설명해 보자.

### 26-13. Program 복습 문제와 답

| 질문 | 답 |
| --- | --- |
| 현재 프로그램이 실행을 시작하는 메서드는? | Program.Main. |
| Main을 실행하려고 new Program()이 필요한가? | 아니다. Main이 static이다. |
| Main에 public이 없으면 진입점이 될 수 없는가? | 아니다. 현재처럼 private인 Main도 진입점이 될 수 있다. |
| STAThread가 프로그램에 스레드를 하나만 허용하는가? | 아니다. 시작 스레드의 COM 실행 방식에 관한 특성이다. |
| ApplicationConfiguration.Initialize가 플레이어 PNG를 로딩하는가? | 아니다. 게임 리소스는 GameMain.Initialize에서 별도로 준비한다. |
| new GameMain()과 game.Run()은 같은 단계인가? | 아니다. 객체·장치 생성과 게임 초기화·반복 실행을 구분한다. |
| using 선언 직후 게임 자원이 해제되는가? | 아니다. 해당 범위를 벗어날 때 해제한다. |
| Run 함수는 어느 클래스에 정의되어 있는가? | 부모 G2AppBase. |
| Update를 반복하려면 Program에 직접 while문을 더해야 하는가? | 아니다. 부모 프레임워크가 반복 호출한다. |
| 정상적으로 창을 닫은 뒤 Dispose는 누가 연결하는가? | Main의 using 선언. |

## 27. GameGlobal.cs 처음부터 끝까지 — 창과 기준 화면의 공통 설정

이 장은 `src/ActionGame/GameGlobal.cs`의 실제 선언 순서를 따른다. GameGlobal은 창 이름과 게임 기준 화면 크기를 한곳에 둔다. **이 파일은 창을 직접 만들지 않고 설정값을 제공한다.**

### 27-01. namespace와 역할 주석

```csharp
namespace ActionGame
{
    // 교수님 예시처럼 게임 전체에서 사용하는 설정을 한곳에 모은다.
```

다른 게임 클래스와 같은 ActionGame 이름 공간이다. 주석은 공통 설정이 여러 코드에 흩어지지 않도록 모아 놓았다는 뜻이다.

이름이 Global이라고 해서 C#의 특별한 전역 변수 문법이 되는 것은 아니다. 개발자가 공통 설정이라는 의미로 붙인 일반 클래스 이름이다.

### 27-02. internal static class GameGlobal

```csharp
internal static class GameGlobal
```

internal은 같은 어셈블리 내부에서 사용할 수 있다는 뜻이다. static 클래스이므로 객체를 만들지 않고 `GameGlobal.ScreenSize`나 `GameGlobal.GameName`처럼 읽는다.

`new GameGlobal()`은 사용할 수 없다. Player처럼 객체마다 다른 위치·체력을 가지는 클래스가 아니라 게임에서 공유할 설정이기 때문이다.

### 27-03. ScreenSize 선언을 단어별로 읽기

```csharp
public static readonly Size ScreenSize = new Size(900, 620);
```

| 부분 | 뜻 |
| --- | --- |
| public | 다른 코드에서 이 필드를 읽을 수 있음 |
| static | 각 객체가 아니라 GameGlobal 형식에 속하는 필드 |
| readonly | 선언 초기화나 해당 형식의 정적 생성자 외에는 재대입할 수 없음 |
| Size | 너비와 높이를 담는 형식 |
| ScreenSize | 필드 이름 |
| new Size(900,620) | 너비 900, 높이 620인 값 생성 |

이 파일의 Size는 System.Drawing.Size다. Windows Forms 프로젝트의 암시적 using 덕분에 이 파일 위쪽에 직접 using System.Drawing을 적지 않아도 이름을 쓸 수 있다.

Size는 클래스가 아니라 **구조체(struct), 즉 값 형식**이다. 여기서 new를 썼다고 반드시 참조 형식 객체라는 뜻은 아니다. 생성자를 호출해 너비·높이를 가진 값을 만든다.

### 27-04. 900과 620은 무엇을 뜻하는가

첫 값은 Width, 두 번째 값은 Height다. 캐릭터 위치의 X/Y가 아니라 화면의 너비·높이다. 다음처럼 읽을 수 있다.

```csharp
int width = GameGlobal.ScreenSize.Width;   // 900
int height = GameGlobal.ScreenSize.Height; // 620
```

이는 게임이 그림과 위치를 계산하는 **기준 화면 크기**다. 실제 모니터 해상도가 1920×1080이라도 게임의 모든 좌표를 1920×1080으로 다시 작성하는 것은 아니다.

기존 경기장 (30,90,840,480), 플레이어 위치, UI 위치는 이 900×620 기준 안에 배치되어 있다. 부모 G2AppBase가 실제 창 크기에 맞춰 같은 배율로 확대하고 남는 공간을 가운데 여백으로 분배한다.

### 27-05. static readonly와 const의 차이

GameRules에서 `public const int MaxHp = 5`를 보았다. GameGlobal에서는 static readonly를 쓴다.

| 비교 | const | static readonly |
| --- | --- | --- |
| 값이 정해지는 방식 | 컴파일 시 상수 표현식 | 실행 시 형식 초기화 과정에서 값 설정 가능 |
| 일반 생성자 호출 결과 사용 | 불가능 | 가능 |
| 초기화 후 일반 코드의 재대입 | 불가능 | 불가능 |
| 현재 예 | GameRules.MaxHp | GameGlobal.ScreenSize |

Size 같은 일반 구조체를 `const Size`로 선언할 수 없으므로 `new Size(...)`로 값을 정하는 설정에는 static readonly가 적합하다.

문자열 리터럴은 const로도 선언할 수 있지만, 현재 GameName은 코드 작성자가 static readonly 필드로 선언한 것이다. “문자열은 const를 사용할 수 없어서 이렇게 했다”는 설명은 틀리다.

### 27-06. readonly Size를 바꾸는 것과 복사본을 바꾸는 것

현재 코드 바깥에서 다음처럼 설정을 다시 넣을 수는 없다.

```csharp
// 설명용 잘못된 코드: 컴파일되지 않는다.
GameGlobal.ScreenSize = new Size(1280, 720);
```

Size는 값 형식이고 이 필드는 readonly이므로 외부에서 이 필드의 Width를 직접 바꾸는 것도 허용되지 않는다.

하지만 복사해 가져온 지역 변수는 별개의 값이므로 바꿀 수 있다.

```csharp
Size copy = GameGlobal.ScreenSize;
copy.Width = 1000;
```

이후 copy.Width는 1000이지만 GameGlobal.ScreenSize.Width는 여전히 900이다. Player처럼 참조 형식 객체의 필드를 공유해 수정하는 예와 구분하자.

GameHud의 readonly brush에서 brush.Color를 바꿀 수 있었던 것은 참조하는 붓 객체의 내부 상태를 바꾼 경우다. 여기의 Size는 값 형식이라는 차이가 있다.

### 27-07. GameName: 창 제목 문자열

```csharp
public static readonly string GameName = "고철 킥! - 폐기장 정리 작전";
```

GameName은 문자열을 저장하는 공통 필드다. 큰따옴표 안의 내용이 초기 문자열 값이다. static이므로 클래스 이름으로 읽고 readonly이므로 일반 코드에서 다른 문자열로 재대입할 수 없다.

string 자체도 불변 형식이다. 문자열 메서드로 새로운 결과를 만들어도 원래 문자열 내용이 그 자리에서 수정되는 것은 아니다. readonly는 그에 더해 **이 필드에 다른 문자열 참조를 대입하지 못하게 하는 제한**이다.

이 값은 운영체제 창의 제목에 사용한다. 게임 안에 그리는 title_logo.png의 글자 그림을 자동으로 바꾸지는 않는다. GameName을 바꾸는 것과 로고 이미지 수정은 서로 다른 작업이다.

### 27-08. GameGlobal의 값은 GameMain을 거쳐 부모에게 전달된다

GameMain의 위쪽 속성을 다시 읽어 보자.

```csharp
public override System.Drawing.Size ScreenSize => GameGlobal.ScreenSize;
public override string GameName => GameGlobal.GameName;
```

GameGlobal에는 설정 **필드**, GameMain에는 이를 돌려주는 override **속성**이 있다. 둘은 이름이 같아도 소속과 종류가 다르다.

부모 G2AppBase는 ScreenSize와 GameName이라는 속성을 사용해 창을 준비한다. GameMain에서 그 속성을 override했으므로 실제로는 GameGlobal의 값을 읽게 된다.

```text
GameGlobal.ScreenSize / GameGlobal.GameName
→ GameMain의 override 속성
→ G2AppBase가 창 크기·제목과 출력 기준으로 사용
```

이 연결 때문에 Program에는 900,620이나 긴 게임 제목을 다시 쓰지 않아도 된다.

### 27-09. 기준 화면과 실제 창 크기가 꼭 같지는 않다

부모 생성자는 기준 크기를 참고하면서 모니터 DPI와 작업 영역에 맞춰 초기 창을 조절한다. 전체 화면에서는 실제 창의 너비·높이로 표시 영역을 계산한다.

```text
동일 배율 = min(실제 창 너비 / 기준 너비, 실제 창 높이 / 기준 높이)
```

1920×1080에 900×620 화면을 표시하면 배율은 약 1.742다. 출력 크기는 약 1567.74×1080이 되고 좌우에 약 176.13씩 여백이 생긴다.

이 배율·여백 계산은 GameGlobal의 두 필드가 직접 수행하는 것이 아니다. GameGlobal은 기준값을 제공하고 G2AppBase.CalculateViewport와 Render2D가 계산·적용한다. 그림의 가로·세로 비율을 유지하기 위해 두 방향에 같은 배율을 쓴다.

### 27-10. ScreenSize만 바꾸면 UI가 모두 자동 재배치되는가

아니다. GameMain의 arena와 GameHud의 많은 좌표·가림막 크기는 현재 900×620에 맞춰 작성되어 있다.

ScreenSize를 1280×720으로 바꾸면 부모의 기준 화면 계산은 달라지지만 기존 UI가 새 기준에 맞춰 자동으로 위치를 다시 계산하지는 않는다. 정상적인 화면 크기 변경을 하려면 관련 레이아웃·경기장·초기 배치도 함께 검토해야 한다.

반대로 “전체 화면에서 더 크게 보여 달라”는 목적이라면 기준값을 바꾸기보다 현재처럼 부모의 확대 변환을 사용하는 것이 맞다. 실제 출력 크기 변경과 게임 설계 좌표 변경을 구분하자.

### 27-11. GameGlobal과 GameRules 비교

| 파일 | 현재 역할 | 대표 값 |
| --- | --- | --- |
| GameGlobal | 창·게임 기준 화면 설정 | ScreenSize, GameName |
| GameRules | 전투·진행 규칙 | MaxHp, KickCooldown, HazardCycle |

두 클래스 모두 static이고 공유 정보를 제공한다. 차이는 “하나는 무조건 수정 가능하고 다른 하나는 불가능하다”가 아니라 **어떤 종류의 정보를 모았는가**에 있다. 현재 선언에서는 const와 readonly 모두 일반 실행 중 재대입을 막는다.

실제 플레이 중 변하는 값은 GameMain, Player, Enemy 등의 인스턴스 필드에 둔다. 예를 들어 score, player.Hp, enemy.FlyTime은 공통 설정값이 아니라 현재 상태다.

### 27-12. Program과 GameGlobal까지 연결한 전체 흐름

```text
Program.Main
→ ApplicationConfiguration.Initialize()
→ new GameMain()
    → 부모 G2AppBase가 창과 장치를 준비
    → GameMain의 ScreenSize / GameName 속성 사용
    → GameGlobal에서 900×620과 게임 제목을 읽음
→ game.Run()
    → GameMain.Initialize에서 GameAssets·GameHud 준비
    → 입력·시간 갱신 / Update / Render 반복
    → 실제 창 크기에 맞춰 동일 비율로 표시
→ 창 종료로 Run 반환
→ using이 GameMain.Dispose 호출
→ 게임 자원과 부모 장치 정리
```

객체를 만드는 과정 내부에는 C#의 필드·생성자 초기화 단계도 있지만, 게임의 역할 연결을 공부할 때는 “UI 설정 → 창·장치 생성 → 게임 자원 초기화 → 반복 실행 → 정리”를 먼저 이해하면 된다.

### 27-14. 두 파일의 핵심을 서술형으로 설명하기

**문제 1: Program.cs가 게임 시작과 종료에서 하는 일을 설명하라.**

답 예시: Program.Main은 게임의 진입점이다. STAThread 특성으로 시작 스레드의 COM 실행 방식을 지정하고 Windows Forms 설정을 초기화한다. GameMain 객체를 만든 뒤 부모에서 제공한 Run을 호출하여 초기화와 게임 반복 실행을 시작한다. using 선언을 사용하므로 Main의 범위를 벗어날 때 Dispose가 호출되어 게임 자원을 정리한다.

**문제 2: GameGlobal.cs와 전체 화면 크기의 관계를 설명하라.**

답 예시: GameGlobal은 기준 화면 크기 900×620과 창 제목을 static readonly 필드로 제공한다. GameMain이 속성을 override해 이 값을 부모 G2AppBase에 전달한다. 부모는 실제 창 크기와 기준 크기로 동일한 가로·세로 확대 비율과 가운데 여백을 계산한다. 따라서 화면을 크게 해도 게임 좌표나 이미지 비율을 개별적으로 다시 변경할 필요가 없다.

**공부 마무리:** Program은 시작과 종료, GameGlobal은 창 설정, GameRules는 규칙, GameMain은 진행, Player·Enemy는 캐릭터 상태, GameHud는 정보 배치, GameAssets는 이미지·소리 자원, GameEffect·ScorePopup은 짧게 남는 화면 효과다. 각 역할에 해당하는 코드 한 줄씩을 직접 찾아 말해 보자.
